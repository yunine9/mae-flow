# Mae-Flow 质量改动统一检视与提交设计

## 目标

把 Construction、Quality 和 Delivery 的改动统一到可恢复、不会循环的提交模型中：普通模式下，任何源码、测试或构建文件改动都必须在验证后由用户检视一次，再精确提交；月光宝盒模式不等待用户，以完整自动证据和晨间报告替代人工停点，尽可能推进到推送完成。

## 核心不变量

1. 主实现、编译修复、Ponytail、CodeCheck 和 UT 都不得自行提交代码。
2. 普通模式下，源码、测试或构建文件只允许在统一检视步骤获得用户确认后提交。
3. 月光宝盒模式跳过人工检视，在机器证据满足后自动生成精确清单、提交并继续；只有权限、冲突、外部依赖缺失或无法安全判断的破坏性操作才停止。
4. Agent 返回使用自然语言；状态机依据真实工具调用、Git 状态和退出码推进，不依赖结果令牌或文件指纹。
5. 所有任务卡必须与 Agent 可用工具一致。配置要求 Skill 时，对应 Agent 必须拥有并实际调用 Skill；配置为明确命令时必须原样执行该命令。

## 状态流

### 初次实现

主 Agent 完成整体实现后调用 compile-agent。编译成功后：

- 普通模式进入统一用户检视；用户要求修改时回到主 Agent 修改并重新编译；用户确认后精确提交。
- 月光模式直接依据当前完整 diff 生成精确提交，记录自动裁决和证据后进入质量阶段。

### Ponytail

每个需求最多执行一轮 Ponytail。若产生源码改动，则调用 compile-agent；普通模式进入统一用户检视并提交，月光模式自动提交。提交后进入 CodeCheck。后续 CodeCheck 或 UT 引发的源码返工不再回跑 Ponytail。

### CodeCheck

CodeCheck 最多执行两轮，每轮为“扫描、范围判断、修复、复验”。首轮无告警直接进入 UT；首轮仍有可修告警时允许第二轮；第二轮后仍有告警则记录风险并进入 UT，不再循环。

CodeCheck 修改源码后先调用 compile-agent：

- 普通模式进入统一用户检视，确认后提交，并从 CodeCheck 重新验证；已消耗的 CodeCheck 轮次不会重置。
- 月光模式自动提交并继续同样的有限轮次。

### UT

UT 使用自适应分批：

- 小范围变更使用一个 UT Agent 完成。
- 大范围变更由 Harness 按修改函数拆成每批 3 至 5 个方法，使用精简任务卡和全新 Agent，避免单个上下文膨胀。
- 分批属于同一个 UT 阶段。各批不提交、不询问用户、不重复读取完整 Spec、Story 和领域文档；任务卡只携带本批相关规格原文、函数范围、代码路径和运行方式。
- 同一 UT 阶段允许累积未提交测试文件，下一批任务卡必须识别这些文件为本轮合法产物。
- 所有批完成后执行一次全量 UT 收口。

仅修改测试时，全量 UT 通过后进入统一用户检视并提交，再进入规格符合性检查。UT 确认并修复被测源码缺陷时，先重新编译，再统一检视并提交，然后从 CodeCheck 重新验证；不回跑 Ponytail。

### 领域归档与交付

领域归档只写 `docs/specs/` 中的长期事实。普通模式下，领域归档确认完成后，交付步骤展示最终精确清单并创建包含尚未提交质量改动和领域文档的提交，然后才能 push。月光模式根据最终 Spec、代码、测试和既有领域索引保守生成并应用归档；不确定内容记录为晨间待办，不编造事实，也不阻塞已验证代码提交与推送。

## 统一检视上下文

统一检视状态记录以下事实，而不是绑定易失的全文指纹：

- 改动来源：initial-build、ponytail、codecheck、ut-test 或 ut-source。
- 检视入口提交和当前未提交文件清单。
- 已完成的编译、CodeCheck、UT 证据摘要。
- 用户确认后的恢复目标。

用户要求调整时，状态机返回与改动类型匹配的修改入口；修改完成后重新执行必要验证。用户确认时只提交精确文件，不提交 `.mae-flow-work/`、Spec、Grill、Story、实施附录或评审报告。

## 兼容与清理

- 更新旧版 `design`、`story_ask`、`rf_verify` 等恢复提示，使其只迁移到当前真实节点，不执行 OpenSpec、UT 蓝图或已删除的计划流程。
- 删除无生产调用的 CP/UT handoff 残留及其导出、测试。
- 保留旧状态到新状态的单向映射，但不得恢复已删除的 CP、逐批提交或指纹重审机制。

## 验证策略

先增加会失败的端到端回归，再修改实现：

1. CodeCheck Agent 修改源码后能够编译、检视、提交并继续，不能在 UT 任务卡处卡死。
2. 多批 UT 能累积未提交测试、完成全量收口，并只触发一次用户检视和提交。
3. UT 修复源码后从 CodeCheck 恢复，不回跑 Ponytail。
4. Ponytail 在同一需求中最多运行一次；CodeCheck 无论结果最多运行两轮。
5. build-fix、AutoUT/java-autout 配置下，Agent 工具声明和真实 Skill 调用契约一致。
6. 领域文档有改动时，交付步骤必须产生提交后才能进入 push。
7. 月光模式覆盖实现、质量返工、领域归档、自动提交和 push 路径，不出现人工确认节点。
8. 完整状态图检查每个可写节点的后继，确保没有“前一步禁止提交、后一步要求工作区干净”的矛盾。

## 非目标

- 不恢复 Construction CP、编码任务拆分或实现子 Agent。
- 不重新引入 Agent 返回令牌、文件全文指纹或因文档细微变化自动重审。
- 不扩大 Ponytail、CodeCheck 或 UT 的业务职责。
