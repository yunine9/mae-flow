# Mae-Flow 使用手册（新手版）

一句话：把一个需求（REQ）或缺陷（DTS）**从单号变成待合入的 MR**，中间的提案、设计、编码、测试、检查、定稿、推送全部由 AI 按固定流程完成。

你在整个过程中只做三类事：**发起**、**在确认点拍板**、**最后去代码平台创建 MR**。流程命令全部由 AI 自己执行，你不需要记任何命令。

---

## 一、开始前的准备（一次性）

以下三件请**自己装好**，缺任何一个流程会直接停下来让你装完再来，AI 不会代装：

| 软件 | 要求 |
|---|---|
| Python 3 | `python --version` 能出版本号 |
| Git for Windows | 自带 Git Bash，`git --version` 能出版本号 |
| Node.js | 版本 ≥ 20.19 |

装好后，在**项目仓库根目录**启动 codeagent 即可。

## 二、第一次使用：环境初始化

第一次发起需求时，流程会先自检环境。你可能遇到：

1. **满屏 ❌** —— 正常。AI 会跑一条安装命令自动装完（几分钟）。**想更省事**：进会话前自己在终端跑
   `python "<插件目录>/scripts/setup.py"`，装完再开工，第一次体验最顺。
2. **一次手动操作**：AI 会贴给你一条环境初始化命令（形如 `comet init …`），复制到终端执行，按提示选 **Claude Code** 平台。跑完回来对 AI 说"好了"就行，后面的目录迁移（.claude → .cac）它自动做。
3. **提示执行 /reload-skills** —— 在会话里敲 `/reload-skills`（或重启会话）。
4. **提示"新装了插件，需重启会话"** —— 重启，然后说一句"继续"，进度不会丢。

> 团队建议：第一个初始化的人把 `.cac/` 和 `openspec/` 目录提交进仓库，之后所有人 clone 下来即用，跳过第 2 步。
> 再建一个 `.mae-flow-defaults.json` 一并提交（内容形如 `{"编译方式": "…", "UT生成方式": "…", "UT运行命令": "…", "测试路径": ["正则"], "源码路径": ["正则"]}`，
> 就是你首单确认过的那几项）——后人交付时这些配置自动预填，确认一下就过。

## 三、标准用法

### 怎么发起

一句话给全两样东西：**单号 + 需求材料**。需求材料形式不限——文档路径、粘贴的内容、甚至一句话口述都行
（口述会被原文落盘成文件让你确认；docx/pdf 这类 AI 读不了的格式，它会请你粘贴关键内容）。例如：

> 交付 REQ2026071801，SE 文档在 docs/se/xxx.md（或直接粘贴内容）
> 交付 DTS2026071902，就一句话：删除好友时未清理会话缓存，偶现崩溃

只说"帮我 init"、"装一下环境"这类模糊的话不会触发流程，AI 会反问你想做什么。

### 什么时候要敲 `/mae-flow`，什么时候不用（高频疑问）

判断只有一个问题：**我是不是要"从零开一个新局"？**
是（交付新单/只装环境/补 STORY/跨仓分解）→ 敲对应命令；不是 → 直接说人话，答案、诉求、问题都行。
另外记住：**"mae-flow"四个字不是咒语**——系统认的是你的意图和当前状态，不是关键词；
"交付 REQ123"和"用 mae-flow 交付 REQ123"效果完全一样，问用法也直接问就行（AI 会先查手册再答）。

| 场景 | 要不要敲命令 | 说明 |
|---|---|---|
| 开始交付一个新需求/缺陷 | **要**（团队规范）：`/mae-flow` + 单号 + 文档 | 显式命令是确定性入口，不依赖 AI 自己"想起来"走流程 |
| 只想装环境，不开始交付 | **要**：`/mae-flow setup` | 单独动作只认显式命令 |
| 只想补生成 STORY 文档 | **要**：`/mae-flow story REQxxx`（带上单号） | 不带单号时 AI 会先和你确认给哪一单补 |
| 需求涉及**多个代码仓** | **要**：先 `/mae-flow chain REQxxx` 做链路分解 | 产出链路文档和各仓启动卡，然后各仓照卡发起（详见 Q6.5） |
| 已交付的单被评审/门禁打回 | **要**：`/mae-flow review-fix`（带单号更稳） | 同单号返工轮次：意见逐条裁决（修/有据反驳/转规格），修完增量检查，commit 自动进原 MR（详见 Q8.2） |
| 进行到一半，不想再走流程 | 可以直接说“退出 mae-flow，保留代码，后面直接改”或敲 `/mae-flow exit` | AI 先展示现场和影响，等你确认后才退出；不会回滚或删除现有代码 |
| 想看使用指南/忘了怎么用 | `/mae-flow help` | 随时可敲，AI 会按本手册给 30 秒上手和答疑 |
| 有一单在途（任何阶段） | **不用**。直接说话 | 每条消息都自动附带流程状态（机制保证，与 AI 水平无关），说"继续"、回答确认点、问进度都行 |
| 会话断了/电脑重启后回来 | **不用**。说"继续之前的交付" | 自动回到断点 |

没敲命令、直接说了"交付 REQxxx"会怎样？明确的交付意图**通常**也能自动进入流程——但这依赖 AI 的识别，不保证。万一它开始绕过流程直接写代码，防护网会在它第一次改源码时拦下并把它拽回流程；不过与其依赖事后纠偏，不如养成敲命令的习惯。

记忆负担其实很小：**只有"从零开始一件事"才需要敲命令（几个入口都长一个样），其余任何时候张口说话就行。**

### 你会经历什么（full 流程）

| 阶段 | AI 做什么 | 你做什么 |
|---|---|---|
| 环境自检 | 实测并自动修复 | 基础件缺失时自己装 |
| 配置确认 | 收集工号、基线分支、单号、需求文档、编译/UT 方式 | **逐项确认**；基线分支和需求文档会单独问你（需求文档会展示内容摘录让你核实是不是这份；只有一段口述需求也行，AI 会原文落盘成文件让你确认） |
| 交付方式选择 | 给出 标准交付 / 缺陷快修 / 小改快过 的推荐及依据 | 拍板选一个 |
| 需求质询（可选） | 按 8 个维度找需求缺口，一次问一题 | 逐题回答（可说"其余按推荐答案"） |
| 提案 / 设计 | 生成提案、规格条目、设计文档 | 看摘要，确认或提修改 |
| STORY（可选） | 生成给测试的 STORY 文档 | **逐项拍板"待确认"项**（比如某章节判"不涉及"对不对——这些是你的决策，AI 无权代答），最后选是否入库（一般不入库） |
| 开发 | 按计划编码、小步提交 | 完成后确认 |
| 验证 | 精简 → CodeCheck → 补 UT → 规格验证 | 有遗留告警时裁决：修 / 正式豁免 |
| 规格定稿确认 | 展示将定稿的规格内容 | **确认（不可逆，犹豫就选暂不定稿）** |
| 推送 | 推送分支、出耗时报告 | —— |
| 创建 MR | —— | 去代码平台用该分支创建 MR 并跟进流水线 |

缺陷快修 / 小改快过 是精简版，跳过设计等重环节，其余相同。

### 核心心智（新手最容易误解的三点）

- **AI 停下来不说话 = 在等你拍板，不是卡住了。** 每个确认点它都必须停，你回复它才继续。
- **AI 说"证据不足，拒绝推进" = 防护机制在工作，不是出错。** 流程只认磁盘上的真实产物，不认口头汇报。让它按报错补齐即可。
- **AI 逐项问你"待确认"不是走过场。** 那些是它无权替你拍板的决策（曾在演练中靠这一环揪出"验收标准要求大数场景、测试没覆盖"的真缺口）。认真答，答完流程才放行。
- **规格确认那几分钟，是全流程你唯一真正要用脑的投资。** AI 会把它自行推断、拿不准的条目逐条问你——
  规格是后面写码、补测、验收的**唯一合同**，那几条答错，代码质量的上限就定错了；这里无脑点过去，
  最后怪模型怪工作流都没用。流程已把要看的压缩到最少（只逼你看推断项），请把脑子花在这几分钟上。

## 四、常见问题

**Q1：对话一直转圈没反应？**
打开 `%TEMP%\mae-flow-hook.log`（PowerShell：`notepad $env:TEMP\mae-flow-hook.log`）看最后几行；重启会话再试；仍复现就把日志发给插件维护人。

**Q2：提示"流程已存在（进行中）"？**
本仓库有一单没走完。说"继续"会自动回到断点；确实不想再走流程，就说：
“退出 mae-flow，保留当前代码，后面直接改”。AI 会先展示当前步骤、分支、未提交文件和退出影响，
等你明确确认后才退出。**不要手删 `.mae-flow.json`**：手删既没有留档，也不能让所有门禁同步退出。

**Q2.5：退出后会丢代码吗？还能直接让 AI 补 UT 吗？**
不会。退出不回滚、不删代码、不删提交，也不删已经生成的文档；流程状态会留在
`.mae-flow-work/exited/` 里。退出后可以像普通会话一样让 AI 改代码或补 UT，但编译、规范检查、
UT、提交和推送不再由本流程强制兜底。以后明确说“重新接回 mae-flow”时会恢复原断点；若退出期间改过源码，
会自动退回对应的编译与检查入口，退出前的质量结果不会拿来凑数。普通的“帮我改一下代码”不会被 AI
擅自解释成恢复流程。若要开始另一张新单，建议另开 worktree，避免覆盖这份退出现场。

**Q3：会话中断了 / 电脑重启了，进度丢吗？**
不丢。开新会话说一句"继续之前的交付"，自动回到断点。

**Q4：AI 被拦了，提示"当前步骤禁止修改源码"？**
正常，每个阶段有权限边界（比如设计阶段不许写代码）。AI 会自己查当前该做什么，你不用管。

**Q5：提交或分支名被拒？**
公司约定是硬性的：分支 `基线分支_工号_单号`，commit `[单号][feat|fix]描述`。工号不要带"域\"前缀。AI 被拒后会自己纠正。

**Q6：想同时做两个需求？**
一个目录同时只能跑一单。用 `git worktree add ../第二目录` 开第二个工作目录，在那边另起会话发起第二单，互不干扰。

**Q6.5：一个需求要改好几个代码仓怎么办？**
分两步走。**第一步，链路分解**：敲 `/mae-flow chain REQxxx`，AI 会读各仓代码查清事实
（触点在哪、现有接口、语言差异），然后逐项问你拍板（边界怎么切、接口契约、谁先谁后），
落盘一份链路分解文档。**第二步，各仓平等交付**：每个仓独立跑流程（同一单号，分支名自动一致），
需求文档就用那份链路文档，交付顺序按依赖（接口提供方先合入），MR 互相注明依赖。
端到端联调不归本流程管，走公司集成流水线。

**Q6.8：交付进行中，我想在这个仓顺手干点别的（看代码/改个无关的东西）？**
看、问、分析随便来，完全不受流程约束。但**改源码会被拦**——你正站在交付分支上，
无关改动会混进这一单的 MR。想改就 `git worktree add ../临时目录` 开个独立目录去改，
干完回来，交付进度纹丝不动。

**Q7：环境步骤返回 BLOCKED？**
只有两类：要你**自己装**的基础软件（见第一节表格），和要你**手动跑**的 `comet init`。按提示做完回来说"好了"。

**Q8：交付完成后怎么开下一单？**
直接说新需求。上一单状态自动备份，无需清理。

**Q8.2：交付完的单被评审意见/流水线打回了怎么办？**
敲 `/mae-flow review-fix`（或直接说"处理 REQxxx 的评审意见"），把意见原文贴给 AI。
它会逐条**先自己查证**再来问你裁决——修 / 有依据地反驳（整理好供你贴回评审系统）/
涉及行为变更的转常规轮次。裁决完按本轮增量依次编译、规范检查、补测、推送，commit 追加进原 MR，不用新建 MR。
返工开始时会冻结原 MR 的 HEAD，后续不会把整个需求重新当成本轮改动；编译、规范修复和 UT 都由
harness 生成完整任务卡再派专项 agent，主会话不能临时猜命令或代写豁免。

**Q8.5：会话用久了 AI 行为变奇怪（重复问、忘规则）？**
长会话的正常退化。直接 `/clear`（或重开会话）——流程状态在磁盘上，说"继续"就回到断点，什么都不丢。
流程也会在进入编码等重步骤时主动提示适合 /clear 的时机，照做即可。
另外：管理员更新过插件后，必须重启会话才生效。

**Q9：感觉 AI 跑偏了 / 行为奇怪？**
对它说：`执行 mae-flow doctor`，会输出项目根、当前步骤、分支、证据、环境的全套体检结果，把结果发给维护人。不要自己用 `goto` 跳步骤——那是管理员通道。

**Q9.5：AI 说"UT 测出代码可能有 bug"，来问我怎么办？**
这是好事——UT 的价值就是揪出真缺陷，不是走过场。AI 会带着自查报告来（失败用例、期望 vs 实际、
规格依据、它的倾向判断），你只需裁决三选一：**确认是代码缺陷**（AI 会解锁修复、重新编译、重跑全部 UT）/
**判定是 UT 理解错了**（AI 让测试 agent 修订用例）/ **本单不修**（隔离该用例，提醒你另立 DTS 单）。
如果 AI 没带自查报告就来问，让它先查清楚再来。

**Q10：UT / CodeCheck 报了遗留问题？**
AI 会列清单等你裁决，两选一：现在修（AI 会为每个问题单独派专项实例）/ 走正式豁免流程。
**没有"忽略"选项**——线上流水线门禁会拦截同样的告警，现在不处理，MR 推上去必然被打回。

如果 CodeCheck 明明执行完成，只是插件暂时看不懂新版本输出，它会保存完整原始结果，不会把解析失败
当成代码有问题，也不会猜成 0 条。你看过报告并确认实际数量后，可以走提示里的人工登记继续；
登记只对当前步骤、当前代码和这份报告有效，代码一改就要重新检查。

## 五、排障命令速查

平时用不到；排障时**直接把左列的话说给 AI** 即可，不用自己敲命令行。

| 对 AI 说 | 作用 |
|---|---|
| 执行 mae-flow status | 看原始进度数据 |
| 执行 mae-flow current | 看当前步骤的完整指令 |
| 执行 mae-flow doctor | 全套体检（排障首选） |
| 执行 mae-flow report | 各阶段耗时 + 摩擦统计（拦截/打回/跳转次数） |
| 执行 mae-flow report --all | 本仓历史交付统计（每单耗时/拦截/打回聚合，交付完成自动记账） |
| 执行 mae-flow envcheck | 全量重测环境（绕过缓存） |
| 执行 mae-flow exit | 展示退出影响；经用户确认后保留现场并退出流程 |

## 六、状态栏

状态栏常驻显示"单号 │ 当前步骤 │ 分支"，交付完成变 ✅。**环境初始化时自动配置，无需手动操作**
（重启会话生效）。没生效时手动兜底——在 settings.json 加：

```json
"statusLine": {"type": "command", "command": "python \"<插件目录>/scripts/statusline.py\""}
```

## 七、术语小表

| 术语 | 含义 |
|---|---|
| 单号 | REQ（需求）或 DTS（缺陷）开头的工单号，决定 commit 类型 feat/fix |
| 基线分支 | 你的工作分支从哪切出、CodeCheck 和 MR 与谁比对 |
| 变更目录 | 本次交付的提案/规格/设计产物所在目录（openspec/changes/ 下，自动创建） |
| 证据 | 流程推进的凭据：真实存在的文件、真实的 git 状态，不是 AI 的口头汇报 |
