# Mae-Flow 稳定基线减法恢复设计

## 1. 背景与目标

当前生产 CLI 在 `cc1841b` 切换到 Lean 工作流后，虽然显著缩短了流程，
但也丢失或弱化了旧流程中已经稳定运行的关键能力，包括子 Agent 的精确输入、
真实编译与质量执行、检查点成熟度、用户输入捕获和端到端差分保护。
后续补齐过程中又出现命令与提示不匹配、重复确认、Reviewer 循环、能力事实代替
真实执行、入口脚本无法定位等问题。

本次恢复以 `d32ccfb` 为唯一代码基线。该提交是生产 CLI 切换到 Lean 引擎前的
最后一个提交，完整测试基线为 1062 个单元测试通过。当前 Lean 代码只作为可选
改进的来源，不作为继续修补的基础。

目标是在旧稳定流程上逐项做减法：保留成熟行为，只删除已经明确确认的厚重环节和
脆弱协议，并选择性吸收当前版本中确有价值的工作目录、Story、领域文档等能力。

## 2. 基本原则

1. 旧流程所有用户可观察行为默认保持，只有本文逐项列出的变化允许改变。
2. 每个实现提交只解决一个行为点，必须能独立验证和回滚。
3. Hotfix、Tweak、Review、配置卡、中文步骤、旧版 Grill 和 Chain 不重写。
4. 稳定性优先于流程缩短；减负不能以删除真实执行或降低可恢复性为代价。
5. 子 Agent 输入必须完整明确，但返回内容不再作为协议解析或门禁对象。
6. Git 提交属于不可逆边界，继续使用精确文件清单；普通文档变化和 Agent 返回不使用
   指纹门禁。
7. 当前 Lean 在途状态通过隔离适配层恢复，不把 Lean 状态机带回旧流程核心。

## 3. 目标主流程

Full 路径收敛为：

```text
配置确认 → 分支 → Grill → 本地 Spec → Story → 开发节奏确认
         → 编码 → 质量验证 → 领域文档与交付
```

### 3.1 保持不变的能力

- 使用旧版中文配置卡、流程名称和交互方式。
- 使用旧版 Interactive Grill，包括八维备课、逐题追问和 Critic 检视。
- 使用旧版 Chain 生命周期、跨仓契约和恢复机制。
- 保留 Hotfix、Tweak、Review 路径的原有用户可观察行为。
- 保留 Staged、Continuous、Adjust 三种开发节奏选择，Agent 不得自行改变选择。

Staged 在每个 CP 完成后停下供用户检视，并按精确清单提交。Continuous 连续完成
全部 CP，最后统一检视和提交。Adjust 允许用户修改 CP 划分后重新确认。

### 3.2 Grill、Spec 与 Story

最终 `grill.md` 保存在单号工作目录，并成为 Story Generator 和 Story Design Reviewer
的强制输入。

`spec.md` 只记录本需求确认后的业务行为、范围、边界和验收标准。它是过程资产，
默认只保存在 `.mae-flow-work/<ticket>/spec.md`，不提交到业务仓，也不执行旧 OpenSpec
物理归档。

Story 是编码前唯一的设计主文档，同时承担软件详细设计、测试交接和轻量 CP 划分。
Story Generator 必须读取：

- 最终 `grill.md`；
- 最终 `spec.md`；
- 本需求相关的 `docs/specs/<domain>.md`；
- 代码调查得到的真实实现事实。

Story 只进行一次设计检视。主 Agent 可以根据意见修正 Story，但普通修正、摘要变化或
文件指纹变化不触发第二次 Reviewer。修正完成后只请求一次最终 Story 用户确认。

### 3.3 Story 章节定义

Story 沿用当前版本已经校正的章节语义：

- 客户场景：描述用户角色、目标和业务价值。
- 场景设计：覆盖正常、边界和失败业务场景。
- 性能规格：只描述容量、最大并发、时延、吞吐、资源占用、兼容性和限制等可度量约束，
  不复制 Mae-Flow Spec 的业务行为规格。
- 验收标准：描述本需求必须达到的可观察功能结果和禁止行为。
- 接口设计：只描述 REST、CORBA、RPC、消息和开放 SDK 等外部或跨组件公开契约。
- 关键函数/方法设计：描述内部新增或修改函数的方法职责、签名变化、核心逻辑、异常语义
  和调用关系。
- 测试设计：记录主要 UT 和接口验证场景，不展开为独立测试蓝图。
- CP 划分：记录每个 CP 的行为结果、主要范围、测试 seam、完成证据和风险，不展开为
  逐行编码计划。

### 3.4 删除的厚重环节

删除独立 Design、Test Blueprint、Roadmap 和详细 Build Plan 阶段及产物。
相应删除 `test-design-agent` 和 `cp-task-analyst-agent`。这些信息中真正有价值的部分
合并进 Story，不再由多份文档重复表达和重复确认。

## 4. 子 Agent 设计

最终保留七个子 Agent：

| Agent | 职责 |
|---|---|
| `grill-critic-agent` | 只读检查 Grill 的需求边界、异常分支和可验收性 |
| `story-generator-agent` | 根据 Grill、Spec、领域文档和代码生成 Story |
| `craft-reviewer-agent` | 执行一次 Story 设计检视，或按配置执行 CP/最终代码检视 |
| `cp-implementer-agent` | 按确认的 Story 和当前 CP 实现生产代码 |
| `compile-agent` | 执行真实编译并处理有限的编译问题 |
| `codecheck-fix-agent` | CodeCheck 有告警时修复并复验 |
| `ut-generator-agent` | 根据最终输入生成并实际运行 UT |

流程仍要求在关键节点真实启动对应 Agent。Mae-Flow 自动生成可读任务卡，提供相关文档
精确路径、代码范围、构建方式和工作目录，但任务卡不携带 SHA 指纹。

调用槽位保持明确且有限：

- Grill Critic 沿用旧 Grill 的备课和收尾两个只读槽位；
- Story Generator 每份最终输入调用一次；
- Story Design Reviewer 调用一次，修正后不复查；
- 启用代码 Reviewer 时，Staged 每个 CP 调用一次，Continuous 在最终增量调用一次；
- CP Implementer 每个 CP 调用一次；
- Compile 对每个实际构建快照调用一次，只有构建输入变化后才产生新槽位；
- CodeCheck Fixer 仅在真实首检存在告警时调用；
- UT Generator 是一个逻辑调用，范围过大时可在该 Agent 内部按旧版协议分批并最终收口。

Hook 只记录 Agent 已启动，以及正常结束、异常中断或超时。以下协议全部删除：

- `XXX_RESULT` 固定首行和固定状态词解析；
- Agent 完成令牌；
- `TASK_CARD_SHA256`；
- 返回字段、数字统计和固定文本格式校验；
- Reviewer 结果与 Spec、Story、源码摘要或指纹绑定；
- 文件变化触发自动复查；
- Agent 失败、超时或返回异常触发自动重试。

Agent 异常时只展示事实、已有产出和风险，由用户决定是否重试或承担风险继续。流程不得
自行形成调用循环。子 Agent 的返回结果不参与 Git 清单授权。

## 5. 编译等待与质量执行

保留 `395d111` 已实现的单次同步编译方案：

- 一轮只启动一次已确认的编译方式，并使用宿主允许的最长超时；已知内部构建目标按约
  十分钟配置。
- 命令返回就是完成信号。
- 禁止后台 `&`、固定 `sleep`、PID 探测、循环轮询和通过 `tail` 日志猜测完成。
- `build-fix` 只调用一次 Skill；显式编译命令同样只同步执行一次。
- 只有源码或构建输入发生实际变化后才能启动下一轮；输入未变化时复用上一轮结果。
- timeout 或 transport failure 如实记录为失败，不切换后台或自动重试。
- CodeCheck Fixer 和 UT Generator 内部需要编译时遵守同一规则。

质量阶段保留真实执行链。CodeCheck 必须先真实扫描，只有发现告警才调用 Fix Agent。
UT Generator 必须真实生成并运行测试。任何“能力事实”命令都不能替代 Compile、
CodeCheck 或 UT 的真实调用。

## 6. Lightcheck

Lightcheck 沿用 `d32ccfb` 的自动范围和建议型执行机制：

- Hook 根据当前提交候选快照自动确定范围，不要求主 Agent 传入 `--file`。
- 只检查本次新增或修改行，以及被本次变更触及的函数。
- 排除未变化的启动前脏文件、测试数据、生成代码和第三方目录。
- 分析超时、工具异常或语法判断不确定时留痕放行，不替代正式 CodeCheck。
- 最多建议修复并复查两轮，不形成流程门禁或循环。

规则包括：正式入参不超过 5 个、有效代码行不超过 50、变更行不超过 120 字符。
圈复杂度规则不再使用，改为函数控制结构最大嵌套深度不超过 5；平行分支和复合条件
不累计。

保留高置信魔鬼数字检查，只扫描本次实际新增或修改的内容行。命名常量、宏、枚举成员、
字符串或注释中的数字、测试数据，以及同行有明确业务解释的数字不报。词法分析无法确定时
不猜测、不误报。

## 7. 领域文档与过程资产

长期领域真相源位于 `docs/specs/<domain>.md`，`docs/specs/index.md` 是轻量路由索引。
流程启动时先读取索引，只加载本需求相关领域文档，不扫描无关领域。

交付时将每个相关领域对账为 `new`、`updated` 或 `unchanged`。领域文档只保留当前业务
真相，不物理保存历次 Spec；新领域自动补充索引，既有领域按最终代码和确认行为更新。
只有实际变化的领域文件进入精确提交清单。

Spec、Grill、Story、决策记录、评审记录、UT handoff 和交付说明默认保存在本地单号
工作目录，不进入业务仓。

## 8. 工作目录、入口与资源迁移

每个需求使用 `.mae-flow-work/<safe-ticket>/`。正常单号直接作为目录名，不附加完整 SHA；
只有两个不同原始单号安全化后发生冲突时，才添加短后缀。

启动后把稳定入口写到 `.mae-flow-work/bin/mae-flow.py`。后续命令只使用该项目本地入口，
不依赖 `CLAUDE_PLUGIN_ROOT`，也不要求 Agent 搜索插件缓存。插件来源只认 CodeAgent 环境。

当前版本的模板、指导文件和必要脚本自动复制到
`.mae-flow-work/plugin-resources/`。Story、Grill、Chain 和任务卡只读取流程输出的精确
资源路径，不在业务仓或用户目录中搜索。

## 9. Git 精确清单

以旧版提交候选和 ownership 检查为主体：自动识别暂存区和同一命令中的候选文件，拒绝
启动前遗留文件、其他需求的 OpenSpec 文件、编译副产物和高置信临时产物，对来源不明但
不一定危险的文件只提示。

选择性吸收当前版本中有价值的精确清单行为：

- 提交前向用户展示精确文件、提交说明和目标分支；
- 初始脏文件必须逐文件确认归属；
- 禁止 `git add .`、`git add -A`、目录、glob 和不透明 pathspec；
- 只允许清单内的精确 `git add -- <files>`；
- 暂存集合必须与确认清单完全一致；
- `.mae-flow-work`、流程控制文件和未点名过程文档禁止入库；
- 清单实际增删后重新展示并确认一次。

不迁移 Lean 的 canonical JSON Delivery Receipt、receipt SHA digest、固定 Git 命令文本、
多层 PostToolUse 观察令牌或强制 `force-with-lease` 命令形态。严格对象是最终提交的文件边界，
不是用户或 Agent 的措辞。

## 10. 在途状态兼容

旧版状态继续原生兼容。检测到当前 Lean 在途状态时先完整备份，绝不原地覆盖。
兼容适配器只迁移：单号、配置、分支、初始脏文件、用户已确认的产物路径和最近一个人工
确认边界。

Agent 令牌、任务卡指纹、Reviewer 摘要、Delivery Receipt digest 等协议状态不迁移。
恢复流程停在最近的安全步骤，并展示一次中文恢复卡让用户确认继续。无法可靠映射时保留
原状态和业务文件，提供恢复建议，不自动猜测阶段。已完成或已退出的 Lean 状态直接归档，
新需求从恢复后的稳定流程开始。

兼容逻辑保持在边缘适配层，不侵入旧流程核心。

## 11. 防回退验证

### 11.1 旧行为 Oracle

以 `d32ccfb` 的 1062 个测试为初始基线。Hotfix、Tweak、Review、Chain、配置卡和 Grill
继续使用差分测试证明行为未变化。只有本文明确删除或改变的行为可以更新预期，且每项变化
必须在测试目录中有可追溯说明。

### 11.2 命令与提示一致性红线

- 所有用户可见命令由真实 CLI 命令模型生成，不维护另一套手写字符串。
- `current`、阶段指导、任务卡和错误恢复提示中的每条命令都必须被同版本解析器接受。
- 每个非终态步骤至少存在一条实际可执行的推进命令。
- 自动遍历状态图，检测死路、无效事件、重复确认和阶段回退循环。
- 用户确认 Story 后，没有真实用户修改时只能进入编码，不能再次要求 Story 确认或 Reviewer。
- 子 Agent 异常不得自动重试。

### 11.3 专项和真实 E2E

专项回归覆盖 Grill 到 Story 的输入链、Story 章节、领域索引、Lightcheck、单次同步编译、
真实 CodeCheck/UT、精确清单、初始脏文件、中文与 Windows 路径、本地入口和资源迁移。

发布前必须在 Windows CodeAgent 环境运行 Full Staged、Full Continuous、Hotfix、Tweak、
Review、跨仓 Chain、中断恢复、Lean 状态迁移、长时间真实编译、CodeCheck 零告警和有告警、
UT 通过和源码缺陷回流，以及最终精确提交与推送。

## 12. 实施与主线切换

所有实现从 `d32ccfb` 派生的恢复分支进行，按以下顺序拆成可独立回滚的提交：

1. 固化旧行为 Oracle 和恢复分支发布门禁。
2. 引入按单号工作目录、项目本地入口和资源自动迁移。
3. 将 Spec 改为本地过程资产，并引入领域文档索引生命周期。
4. 升级 Story 章节和 Grill 输入链。
5. 删除 Design、Test Blueprint、Roadmap、Build Plan 以及两个对应 Agent。
6. 简化七个保留 Agent 的任务卡与返回协议。
7. 保留并加固旧 Lightcheck 范围机制、嵌套深度、魔鬼数字和同步编译。
8. 增加精确清单的用户展示、脏文件归属和清单变化确认。
9. 增加 Lean 在途状态兼容适配器。
10. 完成差分测试、状态图活性测试和 Windows CodeAgent 真实 E2E。

切换前为当前 Lean `main` 创建备份标签。最终恢复分支通过一个双亲合并提交记录当前
Lean 历史，同时保持已验证的恢复分支工作树；随后让 `main` 普通 fast-forward 到该提交，
不 force-push。发布后保留旧差分 Oracle 和真实 E2E 清单，后续流程修改必须持续通过。

## 13. 非目标

- 不继续修补当前 Lean 状态机。
- 不维护经典与轻量两套正式运行时。
- 不重写旧配置卡、中文展示、Grill 或 Chain。
- 不把 Spec、Story 或过程台账默认提交到业务仓。
- 不通过放宽 Git 精确清单来解决子 Agent 协议过严问题。
- 不以模拟能力事实代替真实编译、CodeCheck 或 UT。
