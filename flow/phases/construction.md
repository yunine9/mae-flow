## 目标

按已确认范围分批完成代码，并提前建立后续正式 UT 所需的可测性边界。

## 当前要做

读取当前开发批次简报、已确认 Story 或聚焦范围、相关行为基线、接口变化、可测性
设计、累计 UT 交接和仓库现场。完成每个批次后：

1. 调用一次 `craft-reviewer-agent` 做代码检视，并明确处理每条意见；Task 必须显式
   携带 `current` 中的精确 Spec、Story 路径及本 CP 精确修改文件；
2. 对本批精确改动运行一次 Lightcheck；活跃编码阶段缺少 `--file` 会直接失败；
3. 同步启动一次 `compile-agent`，由它执行启动时确认的构建方式。

`compile-agent` Task 必须显式携带精确 CP、Build 方式、Build 目录及本 CP 修改文件。
C++ 可使用已配置的 `build-fix`，由子 Agent 调用该 Skill；Java 由子 Agent 执行启动时
确认的精确 Maven 命令，其他语言同理。Hook 会记录真实子 Agent 调用；主 Agent 直接
调用 Skill/Bash 或只登记 Build 事实时，`cp-ready` 必须拒绝。禁止等待轮询、后台执行
或自动重试。

每个能力调用前只看本次 `current` 的动态能力区：仍列出对应命令时调用一次，真实返回
后只执行匹配结果的一条命令；已显示“当前语义位置已记录一次”时禁止重复调用。代码
Reviewer 的调用事实和本 CP 检视结论由同一条命令原子记录。其他返回状态同样使用
动态能力区的匹配命令；记录失败不得触发重新检视或重新构建。

Full 路径的每个 CP 都是独立人工检视点，与提交节奏无关：Continuous 只表示最后统一
提交，不表示合并 CP。当前 CP 一旦记录 Build 尝试，源码编辑立即冻结；必须执行
`cp-ready` 展示本批结果并等待用户选择。用户确认后用 `cp-opened --key <下一CP>`
再继续源码修改；用户要求调整则由 `cp-revise` 开放当前 CP 的一次修改与重建窗口。
不得因为一起实现更快而越过 CP 停点。

## 何时询问用户

出现真实歧义、明显设计偏离、不可逆风险，或完整流程的开发批次确认时询问用户。

## 本阶段产出

记录本批简报、实际结果、一次代码检视结论、UT 增量、改动文件、风险和下一批简报。
本阶段不正式编写或运行 UT；本批构建只记录不透明返回事实。

构建完成后先生成本批精确提交计划，再标记当前批次就绪并展示确认卡。用户要求修改
会撤销待执行收据并重新开放代码；确认后冻结本批源码，直到对应分批提交被观察到。

## 下一步

所有开发批次和累计 UT 交接完成后进入质量验证。
