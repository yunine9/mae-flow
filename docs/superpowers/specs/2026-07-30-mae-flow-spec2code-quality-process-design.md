# Mae-Flow Spec2Code 编码质量流程设计

**状态：** 已确认
**日期：** 2026-07-30
**适用范围：** full workflow 的设计后、编码中与最终 UT 阶段

## 1. 背景

Mae-Flow 当前已经具备规格、设计、实现计划、编译、Ponytail、CodeCheck、AutoUT、
规格核对和用户检视等环节，工作流本身已经较稳定。但实际 Spec2Code 产出的代码仍有
两个突出问题：

1. 模块划分、依赖方向、状态所有权和抽象边界不够合理；
2. 代码啰嗦、重复、命名与控制流可读性不足，注释质量不稳定。

现有质量链更擅长在实现结束后发现编译、规范、测试和规格问题，缺少在编码前主动约束
代码落点、编码中按检查点塑形、以及让用户持续纠偏的生产过程。

本设计不以增加 PASS/FAIL 门禁为主要手段，而是补齐以下闭环：

- 编码前由人工审视测试行为和实现任务；
- 编码时向实现 Agent 注入明确的代码职责、复用和注释约束；
- 每个开发检查点由独立 Agent 走读真实代码；
- 用户在所有检视节点都可以提出修改，Agent 修改后再次展示；
- 通过角色化子 Agent 和按 CP 切分上下文，避免长会话导致后半段分析退化。

## 2. 目标

1. 在写第一行代码前明确代码写到哪里、修改哪个符号、承担什么职责。
2. 让每个实现 Task 都能追溯到规格 Scenario、设计决策和测试意图。
3. 让用户在看到局部 CP 时仍然理解完整交付路线，不把计划内延后误认为遗漏。
4. 让独立 Reviewer 聚焦高价值架构与可读性问题，并抑制风格偏好和过度重构建议。
5. 让所有人工检视成为可重复的“展示—反馈—修改—再展示”循环。
6. 让每个子 Agent 只读取完成本职所需的上下文，避免完整会话历史扩散。
7. 统一新增业务注释的语言、内容、格式和审查方式。
8. 保留现有 Compile、Ponytail、CodeCheck、AutoUT 和最终交付链的职责。

## 3. 非目标

1. 不新增代码质量分数或注释覆盖率。
2. 不要求每个类、函数或代码块都有注释。
3. 不让 Reviewer 直接修改代码。
4. 不让用户逐条审阅 2–5 分钟粒度的机械执行步骤。
5. 不在编码前确定测试文件、Fixture、Mock API 等易随实现变化的技术细节。
6. 不为普通意见新增签名令牌或硬阻断门禁。
7. 不让每个细粒度 Task 启动一个独立实现 Agent。
8. 不借本流程清理未触及的全仓历史代码债。

## 4. 核心原则

### 4.1 流程优先于门禁

质量改进发生在设计、计划、编码、走读和用户反馈过程中。编译、静态检查和测试仍然
提供事实证据，但不能替代架构塑形与可读性重构。

### 4.2 全局路线图与局部实现分离

编码前确认所有 CP 的业务合同、Scenario 归属、模块职责、前后接口和延后事项；细粒度
Task 按 CP 即时展开。这样既保留全局可见性，又避免一个 Agent 一次分析全部代码细节。

### 4.3 一次设计、一次技术落地

UT 在编码前只形成稳定的行为蓝图。最终 UT Agent 根据最终代码一次性选择测试文件、
Fixture、Fake/Mock 和具体调用方式，不在每个 CP 维护容易失效的“技术落位”台账。

### 4.4 新鲜实例、角色化上下文

测试设计、Task 分析、CP 实现和代码走读使用职责明确的新鲜实例。Agent 之间传递磁盘上
的结构化结论，不传递完整对话历史。

### 4.5 用户反馈永远可以触发修改

人工检视不是只读展示，也不是一次性审批。用户未明确说“通过/继续”时，流程留在当前
检视环节；用户可以反复提出意见，由 Agent 修改后再次展示。

## 5. 目标流程

```text
需求与设计
  → UT 行为蓝图
  → 人工检视蓝图 Loop
  → 全局 CP 路线图
  → CP1 细粒度 Task
  → Plan Reviewer 检视
  → 人工检视计划 Loop
  → 确认开发节奏
  → CP1 实现
  → Compile Agent 首次编译
  → Craft Reviewer 代码走读
  → 主 Agent 核实意见并组织重构
  → 有源码变化则重新编译
  → 人工检视 CP Loop
  → 使用新鲜实例展开并执行 CP2、CP3……
  → Ponytail
  → CodeCheck
  → AutoUT 按已确认蓝图映射最终代码
  → 规格与最终交付核对
  → 最终代码检视 Loop
```

## 6. UT 行为蓝图

### 6.1 生成时机

设计完成后、生成实现计划前，由新鲜 Test Design Agent 生成。

### 6.2 输入

- 已确认的规格条目与 Scenario；
- 设计结论；
- 需求澄清原话；
- 相关存量行为和兼容约束；
- 代码勘察中的外部依赖与测试条件。

角色任务卡冻结每个输入文件的绝对路径和 SHA256；Task Analyst 还展开勘察笔记点名的
邻近代码文件，避免只拿到一份“代码地图”却看不到实际落点。

### 6.3 内容

每个蓝图条目包含：

```text
场景 ID 与规格来源
测试目的
输入与前置状态
执行动作
可观察结果
必须不存在的副作用
正常、边界或异常分类
建议测试层级
允许替代的依赖
必须使用真实组件的依赖
禁止依赖的实现细节
```

蓝图不包含类名、函数名、测试文件、Fixture 名称、Mock API 或 private 调用。
场景 ID 在同一蓝图内必须唯一；重复 ID 直接退回蓝图 Loop，不能在 AutoUT 前静默合并。

### 6.4 人工检视 Loop

首次展示完整蓝图。用户可以直接给出修改意见；Agent 复述本轮修改理解，更新蓝图并做
Scenario 覆盖与内部一致性检查。后续只展示修改差异和受影响条目，直到用户明确继续。

蓝图保存到：

```text
.mae-flow-work/test-blueprint-{单号}.md
```

## 7. 全局 CP 路线图

### 7.1 路线图内容

编码前生成所有 CP 的：

- 业务目标；
- 完成合同；
- 明确非目标；
- Scenario 归属；
- 主要模块职责；
- 状态所有权；
- 向后续 CP 提供的接口；
- 依赖的前序接口；
- 延后事项及其具体落点；
- 关键风险。

路线图保存到：

```text
.mae-flow-work/roadmap-{单号}.md
```

### 7.2 CP 检视卡

每次 CP 代码检视都必须重新展示以下派生视图：

1. 整体交付地图与各 CP 状态；
2. 当前 CP 的完成合同与非目标；
3. 未实现行为对应的后续 CP 和 Task；
4. Scenario → CP → Task → 状态覆盖表；
5. 当前 CP 对后续暴露的接口；
6. 当前 CP 的实际代码 diff。

“后续处理”不是合法说明。延后事项必须指向具体 CP 和 Task；无法指向时视为计划缺口，
进入计划修改 Loop。

## 8. 细粒度实现 Task

### 8.1 粒度

CP 是可观察的业务切片；Task 是精确代码落点。一个 CP 通常包含多个细粒度 Task，由同一
新鲜 CP Implementer 连续执行。

Task 通常只包含：

- 一个主要文件；
- 一个主要类、函数或接口；
- 一个清晰职责；
- 一组紧密相关的行为；
- 一次可以独立检查的代码修改。

以下内容属于机械 Step，不作为用户逐条检视对象：搜索符号、编辑一行、执行单条命令、
更新 import、提交文件。

### 8.2 固定格式

```text
Task ID 与所属 CP
目标
创建/修改文件
目标类、函数或接口
精确函数签名
输入、输出与错误语义
主要控制流约束
状态所有权
必须复用
禁止事项
注释计划
对应 UT 蓝图场景
完成后的定向检查
```

Task 规定代码合同，不包含完整实现代码。允许写精确签名、必要伪代码和控制流约束。

### 8.3 即时展开

编码前完整展开 CP1；后续 CP 先保留完成合同、接口和 Task 摘要。进入 CPn 前，由新鲜
CP Task Analyst 根据最新路线图、前序接口和相关代码展开细粒度 Task。

若展开结果改变全局模块边界、Scenario 归属或前序接口，必须先更新路线图并进入人工
计划检视 Loop。

## 9. Plan Reviewer

Craft Reviewer 以 `PLAN` 模式只读检查当前 CP 的 Task：

- 文件与符号落点是否正确；
- 是否按业务职责拆分；
- 状态和依赖所有权是否清晰；
- 是否遗漏相关 Scenario；
- 是否复用已有实现；
- 是否引入无现实使用者的抽象；
- 前后 CP 接口是否一致；
- 注释计划是否具体；
- Task 是否过粗或只是机械步骤。

Reviewer 每轮最多提出五个高价值问题，并使用第 13 节的统一发现格式。主 Agent 技术
核实并修订计划后，向用户展示按 CP 分组的 Task 摘要和未决取舍。

## 10. 子 Agent 分工

### 10.1 主 Agent / Coordinator

- 与用户对话并保存用户原话；
- 维护全局路线图和人工检视 Loop；
- 生成角色化任务卡；
- 对 Reviewer 意见做技术核实和处置；
- 处理跨 CP、外部契约和需求范围决策；
- 不长期持有全部代码细节。

### 10.2 Test Design Agent

每个需求一个新鲜实例。只生成和修订 UT 行为蓝图，不写测试或业务源码。

### 10.3 CP Task Analyst

每个 CP 一个新鲜实例。只展开当前 CP 的细粒度 Task，不写业务源码。

### 10.4 Craft Reviewer

每次派发都使用新鲜实例，支持两种只读模式：

- `PLAN`：编码前检查 Task；
- `CODE`：首次编译后检查当前 CP 的真实 diff。

同一 CP 的 PLAN 与 CODE 检视也不复用实例；两者读取各自任务卡，避免计划阶段的判断
污染对真实实现的独立观察。Reviewer 不直接改代码，不执行编译，不补 UT，不扩大为
全仓审计。

### 10.5 CP Implementer

每个 CP 一个新鲜实例，连续执行当前 CP 已确认的全部 Task。发现设计、规格或路线图
矛盾时停止并返回具体事实，不自行改变计划边界。

### 10.6 现有质量 Agent

- Compile Agent：编译与编译失败修复；
- CodeCheck Agent：规范告警修复；
- UT Agent：根据蓝图映射最终代码、生成并运行测试。

## 11. 角色化上下文包

所有 Agent 都读取固定 Coding Charter，但业务上下文按职责裁剪：

| Agent | 业务输入 |
|---|---|
| Test Design | 规格、设计、澄清、存量行为 |
| CP Task Analyst | 路线图、当前 CP 合同、相关 Scenario、代码勘察、邻近代码 |
| CP Implementer | 已确认 Task、当前 CP 编码简报、目标文件、前序公开接口 |
| Craft Reviewer PLAN | 当前 CP 合同、Task、路线图、相关代码事实 |
| Craft Reviewer CODE | 当前 CP 合同、实际 diff、直接集成边界、既有模式 |
| UT Agent | UT 蓝图、最终规格、最终代码范围、测试配置、既有测试样例 |

任何 Agent 都不默认读取完整会话历史。用户反馈以原文落盘；跨 Agent 传递结构化结论和
明确路径，不传递推理过程。

## 12. 编码前提示词注入

每个 CP Implementer 开工时注入：

### 12.1 固定 Coding Charter

1. 优先复用仓库现有模块、接口和模式。
2. 每个类、函数和文件只承担一个可描述职责。
3. 业务状态必须有明确所有者。
4. 依赖方向遵循已确认架构。
5. 优先用命名、接口和控制流表达意图。
6. 注释只解释原因、约束、契约和删除条件。
7. 不为当前规格未要求的未来需求增加扩展点。
8. 代码应能通过公开行为验证，避免依赖 private 状态的设计。

### 12.2 当前 CP 动态编码简报

- 当前职责和非目标；
- 模块与状态所有权；
- 必须复用的实现；
- 错误和兼容语义；
- 必须解释的注释；
- 相关 UT 蓝图场景；
- 前序接口和后续接口约束。

动态简报只能来自已确认设计、路线图、代码勘察、UT 蓝图和用户原话。Agent 不得现场
发明新的架构约束。

## 13. Reviewer 发现与处置

### 13.1 发现格式

每条意见必须包含：

```text
问题与代码位置
依据：违反的规格、设计、Task、编码简报或仓库模式
证据：调用链、已有实现、重复代码或可复现后果
实际影响
最小改法
```

缺少依据或证据的意见不进入修改队列。

### 13.2 Reviewer 限制

- 每个 CP 最多五条高价值问题；
- 只看当前 CP diff 和直接集成边界；
- 提重复实现前必须定位已有实现；
- 不接受纯假想扩展或个人风格偏好；
- 两种写法都正确时只描述取舍，不要求修改；
- 禁止顺手清理未修改的存量代码；
- 复查只验证已接受意见和本次修改引入的直接回归，不扩展新一轮审查范围。

### 13.3 主 Agent 四类处置

1. **修改**：合同违反、明确职责错误、重复实现或当前可证明的维护问题；
2. **验证后修改**：结论可能成立但需查调用方、历史行为、测试或配置；
3. **人工裁决**：存在两个合理方案，或会改变设计、外部契约、范围、依赖；
4. **拒绝/暂缓**：风格偏好、假想未来、过度抽象、无关旧债或缺少证据。

每个 CP 保存处置记录，避免 `/clear` 后重复讨论：

```text
.mae-flow-work/reviews/{单号}/{CP}-plan.md
.mae-flow-work/reviews/{单号}/{CP}-code.md
```

记录顶部必须带冻结信封：`CLEAN|FINDINGS`、PLAN/CODE 模式、CP、角色任务卡
SHA256、被审计划或源码快照 SHA256。只有显式 `CLEAN` 才允许零条 Finding；
`FINDINGS` 至少一条。信封与当前任务卡或审查目标不一致时必须重新派 Reviewer。
首次 build_plan 的完成证据也必须包含 CP1 PLAN Review，不能只凭 roadmap/plan 文件存在推进。
用户确认当前 CP 计划前再次核对 plan 与 Review 文件摘要；展示后任一文件变化都会
清除旧收据并返回计划 Loop。

## 14. CP 编码与走读 Loop

每个 CP 执行：

```text
新鲜 CP Implementer 执行 Task
  → Compile Agent 首次编译
  → Craft Reviewer CODE 模式走读
  → 主 Agent 核实并组织修改
  → 源码变化则重新编译
  → 用户检视 CP
  → 用户提出意见则修改、重新编译并定向复查
  → 用户明确继续后进入下一 CP
```

首次编译保证 Reviewer 看到至少能够构建的代码。Reviewer 不修改源码；主 Agent 可以
核实和裁决意见，但代码修改重新交给当前 CP Implementer。用户在 CP 检视 Loop 中提出
的代码意见也由该 Implementer 处理。任何修改都必须保留在当前 CP 范围内；扩大模块
边界时进入计划或设计 Loop。

## 15. 统一人工检视 Loop

UT 蓝图、实现计划、每个 CP 代码和最终代码统一使用：

```text
Agent 产出
  → 展示给用户
  → 用户直接给出修改意见
  → Agent 复述本轮理解
  → 修改并做一致性检查
  → 展示差异和受影响部分
  → 用户继续修改或明确通过
```

规则：

- 用户不必先选择“需要调整”，可以直接说修改内容；
- 人工修改轮次不设上限；
- 首轮展示完整内容，后续优先展示差异；
- 用户反馈保存原话；
- 用户未明确通过时不进入下一环节；
- 只重新分析受影响部分，但源码变化后的编译和相关测试必须使用新版本；
- 用户要求改变需求或设计时，回到对应上游 Loop。

## 16. Comment Standard v1

完整规范作为 Mae-Flow 固定资源：

```text
runtime/standards/comment-standard-v1.md
```

任务卡携带规范版本和路径；各 Agent 读取同一份真相源。

### 16.1 语言

- 新增业务注释统一使用简体中文；
- 代码符号、协议名、错误码和命令保留英文原文；
- 公共 API 使用语言原生 Doc 语法，正文使用中文；
- 不强制翻译未修改的历史英文注释；
- 使用完整句子和中文标点；
- 单行不超过 120 列。

### 16.2 允许内容

注释只解释：

1. 为什么这样实现；
2. 什么业务不变量或技术约束不能破坏；
3. 调用者必须知道的错误、副作用、并发和兼容契约；
4. 临时代码存在的原因和删除条件。

禁止逐行翻译代码、注释掉的旧代码、修改历史、无依据警告和无问题单 TODO。

### 16.3 局部注释

- 放在目标代码正上方，不使用行尾注释；
- 优先通过重命名、拆函数和拉平控制流消除注释需求；
- 超过三行仍说不清时，将完整原因放入设计文档，代码只保留约束摘要。

### 16.4 公共 API

新增或修改的公共 API 按语言原生格式表达以下存在项：

- 一句话职责；
- 前置条件；
- 行为约束；
- 参数非显然语义；
- 返回值；
- 错误语义；
- 副作用；
- 并发或线程安全。

不存在的章节不保留空模板。实现与接口契约完全一致时继承接口文档，不复制。

### 16.5 TODO 与 FIXME

只允许：

```text
TODO(<问题单>): <待完成动作>；删除/完成条件：<明确条件>。
FIXME(<问题单>): <当前已知缺陷>；临时处理：<当前方案>。
```

无问题单、无动作或无结束条件的 TODO/FIXME 不允许新增。

### 16.6 Task 注释计划

每个 Task 必须写：

```text
注释计划：
- ADD：<符号>，<需要解释的原因或约束>。
- UPDATE：<符号>，<需同步的契约>。
- REMOVE：<位置>，<通过何种重构消除无效注释>。
```

确实不需要时写：

```text
注释计划：
- NONE：行为可由类型、命名和控制流完整表达。
```

禁止“适当补充注释”等模糊表述。

### 16.7 多阶段注入

- CP Task Analyst：生成 Task 注释计划；
- CP Implementer：读取完整规范，Prompt 注入八条精简核心规则和动态注释计划；
- Craft Reviewer PLAN：检查注释计划是否具体；
- Craft Reviewer CODE：检查是否应先重构、是否遗漏 why、注释是否准确和符合格式；
- UT Agent：测试代码同样遵循规范，测试注释只解释非显然场景、数据和替代策略。

## 17. 最终 AutoUT

最终 UT 任务卡输入：

- 人工确认的 UT 行为蓝图；
- 最终规格；
- 最终业务代码范围；
- 仓库测试配置；
- 既有测试写法；
- Comment Standard v1。

UT Agent 一次性完成行为蓝图到最终接口、测试文件、Fixture 和 Fake/Mock 的映射，并输出：

```text
蓝图场景 → 测试用例 → 执行结果
```

无法实现的测试分为：

1. 测试实现或工具能力问题：由 UT Agent 在自身修复预算内处理；
2. 生产接口缺少合理 test seam：返回对应代码事实，回当前 CP 重构；
3. 蓝图理解错误：进入 UT 蓝图人工检视 Loop；
4. 需求或设计变化：回规格或设计流程。

任何源码重构后重新执行受影响的编译、Craft Review、Ponytail、CodeCheck 和最终 UT。

## 18. 恢复与上下文治理

流程恢复只依赖以下磁盘产物：

- 规格与设计；
- UT 行为蓝图；
- 全局 CP 路线图；
- 当前细粒度实现计划；
- 每个 CP 的 Plan/Code Reviewer 发现与处置；
- Task 完成状态和接口结论；
- Git 历史与当前 diff；
- 用户反馈原话。

安全的上下文切换点：

- UT 蓝图人工确认后；
- 实现计划人工确认后；
- 每个 CP 用户确认后；
- 最终 UT 完成后。

新鲜 Agent 不读取完整历史，只读取本角色任务卡列出的产物和文件。若任务卡无法说明
当前职责、允许范围、输入和期望输出，Agent 必须返回上下文缺口，不自行扩大阅读范围。

## 19. 异常与回流

| 发现 | 回流 |
|---|---|
| UT 蓝图遗漏或错误 | UT 蓝图 Loop |
| Task 文件落点或职责错误 | 当前 CP 计划 Loop |
| 全局模块边界或 CP 归属错误 | 全局路线图/设计 Loop |
| 代码可读性或局部职责问题 | 当前 CP 代码 Loop |
| 需求行为变化 | 规格流程 |
| 重大技术方案变化 | 设计流程 |
| 编译失败 | Compile Agent |
| 最终 UT 暴露源码缺陷 | 对应 CP 代码 Loop |

回流后只复用仍绑定当前产物和源码的事实；受修改影响的 Agent 结论、编译和测试结果重新
产生。

## 20. 验收标准

流程实现后应通过代表性 Spec2Code 案例验证：

1. 用户在编码前能看到全部 CP 的目标、Scenario 和延后落点；
2. CP1 的细粒度 Task 能明确回答“去哪写什么代码”；
3. 后续 CP 使用新鲜 Task Analyst，Task 质量不因主会话长度下降；
4. 每个 CP 使用新鲜 Implementer 和 Craft Reviewer；
5. Reviewer 每轮不超过五条，并且每条都有依据、证据、影响和最小改法；
6. 用户可以在所有人工检视节点反复要求修改；
7. CP 检视能区分本轮遗漏和计划内延后；
8. 最终 UT 不重新发明业务期望，能输出蓝图到测试用例的完整映射；
9. 新增业务注释符合 Comment Standard v1；
10. 与当前流程相比，独立盲审中的模块边界、重复实现和可读性问题明显减少；
11. 总 Agent 数和上下文读取范围可以从任务记录中解释，不出现无界并发或重复全仓分析。

## 21. 建议实施顺序

1. 固化 Comment Standard v1 和通用人工检视 Loop；
2. 增加 UT 行为蓝图及人工检视流程；
3. 增加全局 CP 路线图、细粒度 Task 模板和 Plan Reviewer；
4. 增加按 CP 的 Task Analyst 与 Implementer 上下文包；
5. 在现有 build 检查点中加入首次编译后的 Craft Review 与修改 Loop；
6. 调整最终 UT 任务卡读取行为蓝图；
7. 用历史真实需求做当前流程与新流程的 A/B 试运行，再校准 CP 大小和 Agent 数量。
