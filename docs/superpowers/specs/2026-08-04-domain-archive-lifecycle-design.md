# 领域归档与过程件本地化设计

## 1. 目标

Mae-Flow 的需求过程件全部留在项目本地工作区。质量验证完成后，流程把本次已经确认、实现并验证的长期知识归档进领域真相源；仓库不保存需求过程流水。

文档类交付物只允许是实际新增或变化的：

- `docs/specs/<domain>.md`
- 新领域所需的 `docs/specs/index.md`

业务源码、测试、必要构建配置和资源仍按正常精确交付清单提交。

## 2. 明确不上库的内容

以下文件或等价内容全部位于 `.mae-flow-work/<单号>/`，不得进入 Git 交付清单：

- Spec、Grill、Story、需求澄清记录和决策记录；
- Story/CODE Reviewer 记录、评审返工台账；
- UT handoff、验证报告、CodeCheck 豁免说明和诊断日志；
- Delivery Notes、任务卡、过程计划、状态备份和能力执行记录；
- OpenSpec change、归档副本或其他按单号保存的规格过程文件。

旧在途流程已经提交的历史文件不删除、不改写。尚未提交的过程文件迁入本地工作目录。

## 3. 流程位置与数据流

新增唯一可达的“领域归档”阶段，位于完整质量验证之后、最终代码检视和精确交付清单之前。Staged 和 Continuous 均只执行一次领域归档，不在 CP 中间更新领域文档。

归档输入为只读事实：

1. `.mae-flow-work/<单号>/spec.md`；
2. `.mae-flow-work/<单号>/grill.md`；
3. `.mae-flow-work/<单号>/story.md`；
4. 最终业务源码、测试和配置差异；
5. `docs/specs/index.md` 路由出的相关领域文档。

归档先在 `.mae-flow-work/<单号>/domain-archive/` 生成候选和摘要，不直接修改仓库文档。每个领域只能得到以下结论之一：

- `new`：新建领域文档，并为新领域更新索引；
- `updated`：更新已有领域的当前真相；
- `unchanged`：本次没有新增长期知识，不产生提交文件。

用户检视归档摘要和候选 diff 后确认一次。确认后才应用候选到 `docs/specs/`，并把实际变化的精确路径交给最终交付清单。

## 4. 领域文档模板

插件提供固定模板，并在项目初始化时复制到 `.mae-flow-work/plugin-resources/assets/DOMAIN-SPEC-TEMPLATE.md`。模板包含以下必需章节：

1. 领域目标与边界
2. 核心术语与不变量
3. 可观察行为与业务规则
4. 对外及跨组件契约
5. 数据、状态与兼容性
6. 性能、容量与资源限制
7. 异常、降级与恢复
8. 验证方式与测试关注点
9. 代码落点索引
10. 明确不包含的范围

领域文档禁止写入单号、CP、开发过程、Reviewer 记录、提交记录和临时方案。新领域严格从模板创建。已有领域只在本次触及时补齐缺失章节，不执行全仓批量迁移；已有自定义内容必须保留。

模板校验要求章节存在且具有实质内容，不要求逐字格式一致。明确不适用的章节必须写出领域依据，不能留空或只写“无”。

## 5. 生成与维护

归档先根据 Spec、Grill、Story、代码路径和符号提取领域关键词，再通过 `docs/specs/index.md` 定位相关领域。命中已有领域时生成增量候选；只有没有匹配领域时才能建议新领域名称和关键词。

归档内容必须引用已经确认的行为和最终代码事实，不得补写推测。已有领域文档保存当前有效真相：旧规则被替换时直接更新原章节，不追加按单号的历史流水；Git 历史承担版本追踪。

一个需求可以归档到多个领域。每个领域独立展示依据、结论和 diff。候选生成后，如果 Spec、Grill、Story、最终代码输入或相关领域文档发生变化，候选标记为过期，只重新生成归档候选，不回退编码、不重跑 Reviewer 或质量链。

## 6. 消费

Grill 备课、Story 生成、CP 实现、CodeCheck 和 UT 任务卡统一通过领域索引按关键词加载相关文档，禁止全量读取 `docs/specs/`。

索引条目由领域名、关键词和固定文档路径组成。重复领域名、非法路径、缺失文件和重复关键词归属必须产生明确诊断。索引或文档不完整时给出唯一可执行修复命令，不自动重试、不形成流程循环。

归档阶段消费本地过程件，其他阶段只消费已经入库的领域真相源；未确认的归档候选不得成为下游依据。

## 7. 命令与状态

新增确定性命令：

- `domain-archive prepare`：冻结输入并生成本地候选和摘要；
- `domain-archive show`：显示领域结论、依据和候选 diff；
- `domain-archive apply --message-id <ID>`：校验用户确认和输入新鲜度后应用候选；
- `domain-archive status`：显示当前归档状态和唯一恢复动作。

状态保存可读的输入路径、候选路径、领域结论、用户确认状态和实际应用路径，不依赖 Agent 返回格式、任务卡摘要或源码指纹。新鲜度依据输入文件的可重算内容摘要和 Git 最终差异事实；摘要只用于拒绝应用过期候选，不触发阶段回退或自动重试。

`unchanged` 是合法完成结果。所有领域均为 `unchanged` 时，用户确认“无需更新领域文档”后继续生成仅含实现文件的交付清单。

## 8. Git 边界

最终 Manifest 只允许：

- 本次业务源码、测试、必要配置和资源；
- 本次 `domain-archive apply` 实际写入且内容发生变化的领域文档；
- 新领域实际需要更新的 `docs/specs/index.md`。

Manifest 必须拒绝 `.mae-flow-work/`、`docs/clarifications-*`、`docs/review/REVIEW-*`、`docs/codecheck-exempt-*`、`docs/delivery-notes.md`、`docs/story/`、OpenSpec change/archive 和其他未由归档应用产生的过程文档。

文件、提交说明或目标分支变化时，仍按现有精确清单规则重新确认一次；相同清单不得重复提问。

## 9. 错误处理与恢复

- 模板缺失或损坏：拒绝生成候选，提示恢复项目本地资源；
- 索引损坏：列出具体行和唯一修复命令，不猜测领域；
- 候选内容缺章或含过程元数据：拒绝 `apply`，保留候选供修正；
- 输入变化：标记候选过期，提示重新 `prepare`；
- 应用部分失败：使用原子文件替换，不留下半套领域文档或索引；
- 用户不确认：候选留在本地，流程停在可恢复归档状态；
- 无长期知识变化：以 `unchanged` 正常完成，不制造空提交。

任何错误都不得重派 Agent、自动重试命令或回退已完成的编码、Reviewer 和质量步骤。

## 10. 验证

自动化必须覆盖：

- 新领域、已有领域更新、全部无需变化和多领域归档；
- 模板生成、章节校验和已有文档触及时迁移；
- 候选输入变化后的过期拒绝；
- 相关领域按索引消费且不全量读取；
- 原子应用和中途失败恢复；
- 所有过程文档无法进入 Manifest；
- 旧 Clarifications、Review、Delivery Notes、CodeCheck 豁免和 OpenSpec 提交路径不可达；
- Staged/Continuous 均只在最终质量后归档一次；
- 所有流程提示命令均可由生产 parser 解析；
- 每个可达非终态有真实后继，错误恢复不会形成循环。
