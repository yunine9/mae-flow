# 编码执行方式:新上下文(L3)

仓库预设 `.mae-flow-defaults.json` 写 `"编码执行方式": "新上下文"` 时,build 步改按本协议执行。
默认(未设置或 `"主会话"`)不走本文,主 Agent 亲写,一切照旧。

## 为什么存在这个模式

长会话尾部写码,注意力已被四个阶段的对话稀释——被否掉的方案、中途改过的主意
都还躺在上下文里(lost-in-the-middle)。本模式做一次干净的倒置:

- **老上下文不再生成代码**,只干它真正擅长的:拆工单、验收 diff、
  用它记得的用户意图纠偏;
- **新上下文(实现子 Agent)只看文档**,不带包袱地按用户确认过的版本实现。

前提是文档足够承载决策——实施附录瘦身(只留任务边界+接口契约,禁代码块)
就是为此铺的路。文档承载不了的需求,本模式会放大缺口而不是掩盖:
工单写不成自包含,就退回主会话亲写,这是信号不是失败。

## 协议

1. 主 Agent 读三份文档与编码基准(照常),按 `implementation.md` 的任务边界
   逐任务出**自包含工单**:三份文档的精确路径、该任务的文件清单与单一职责、
   接口契约两栏原文、编码基准路径,并写明"所需信息全在本工单内,
   不回放聊天记录"。
2. 每个工单派一个实现子 Agent(通用型,可写码,禁 git 操作)。任务间有
   接口依赖时按顺序派,无依赖可并行;**上一任务的产出签名进下一工单**
   (契约两栏就是干这个的)。
3. 子 Agent 返回后,主 Agent 通读其全部改动,执行 build 步的四项自查与
   跨块漂移检查——**产出不免检**,这条与机械扇出同款,不因模式放宽。
4. 全部任务完成后照常:一次 COMPILE 任务卡、一次人工检视。
   门禁与证据一个都不变。

## 边界(与主会话模式共用的铁则)

- 工单写不成自包含 → 该任务回主会话亲写;
- 子 Agent 卡住/返回 NEEDS_INPUT → 修工单重发,不替它补产出;
- 主 Agent 在验收中发现文档有缺口 → 停,走既有的"缺口回实施附录订正"通道,
  不在工单里口头补需求。
