# 空交付清单修复设计

## 根因

稳定流程在用户检视代码后提交实现，质量阶段产生的修改也会在统一检视后提交。领域归档随后允许合法选择 `unchanged`。当本单没有领域文档变化时，进入 `delivery_review` 后已经没有尚未提交文件，但现有 manifest 契约仍要求非空文件清单和一笔新提交，形成不可满足的状态。

旧 CP 在途状态热切换不纳入本次兼容范围；新流程不迁移旧 CP 任务卡或检查点现场。

## 方案

采用受约束的空交付清单，保留统一的 `delivery_review → push` 状态路径，不跳过交付证据，也不把已提交源码重新加入清单。

- `manifest set --unchanged --target <分支>` 与 `--file` 互斥。
- 仅当领域归档已经 `applied`、结果为 `unchanged`、`applied_paths` 为空时允许。
- 当前新增脏文件必须为空；流程启动前已有且指纹未变化的文件可继续留在工作区，并记录进空清单供证据复核。
- 空清单自动确认为 `no-op`，不再次询问用户，不执行 `git add` 或 `git commit`。
- `delivery_manifest_committed` 对空清单验证上述事实后直接通过；普通非空清单继续保持原有用户确认和精确提交门禁。
- 最终步骤明确禁止把已经提交的源码、测试或构建文件拿来填充空清单。
- 当前活跃提示和错误信息不得再使用“分段编译”或引导 Compile 前提交；旧词只允许存在于历史迁移测试中。

## 验收

- 代码已提交、领域归档 `unchanged`、工作区无本单新脏文件时，空 manifest 无需新提交即可进入 push。
- 领域归档未完成、有领域文件变化或存在新的未提交文件时，空 manifest 必须拒绝。
- 非空 manifest 的确认、精确暂存和提交规则保持不变。
- 新流程活跃资源中不再出现 CP/分段编译恢复话术。
- 运行针对性测试、全量单测、`scripts/selftest.py` 和 `git archive` 自检。
