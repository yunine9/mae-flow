自动获取并向用户展示完整配置(获取不到的询问):
- 工号(whoami 或 git config user.name;Windows 的 whoami 返回「域\用户名」,只取反斜杠后的部分——反斜杠不能进分支名)
- 基线分支:执行 git branch --show-current 作为候选值，连同用途一起放进最终配置确认单；
  用户可在最终确认时选择修改为 master / develop / release 等其他分支。**不要为这一项单独再问一次确认**。
- 单号:用户输入,REQ→feat / DTS→fix。**多个单号必须先问用户拆分还是合并、主单号取哪个**
- 跨仓交付(仅当需求涉及多个代码仓时问,不涉及不提):跨仓需求应**先有链路分解文档**
  (/mae-flow:mae-flow chain 的产物 CHAIN-<单号>.md:各仓职责、接口契约、依赖顺序);
  有 → 本仓需求文档=该 CHAIN 文档(+原需求),按其中本仓职责交付,MR 注明依赖的他仓 MR;
  没有 → 建议用户先执行 /mae-flow:mae-flow chain 做链路分解再回来,用户坚持直接做则如实记录风险。
  各仓地位平等,不存在主从;链路文档存放在哪个仓只是存放地。
  **回流条款**:本仓交付任何阶段发现 CHAIN 文档错漏(漏触点/契约不够用/顺序不对)→ 停下报告用户,
  修订 CHAIN 文档(升版本号+记变更)并提醒用户同步给其他仓,禁止本仓自行绕开文档瞎适配
- 需求文档:先记住:**单号与需求完全解耦**——单号只用于
  git 分支/commit 命名,与需求内容互不推导,各自必填。按用户实际情况三分支:
  ① 用户已给路径 → 先尝试读取。**可读**(md/txt/代码内注释等文本格式)→ 展示路径 + 标题/首段摘录,
    把路径和标题/首段摘录放进最终配置确认单(防路径对文件错);**不可读**(docx/pdf/图片等二进制,或读出来是乱码)→
    如实告知"该格式无法直接读取",请用户粘贴关键内容或提供文本版——粘贴的按 ② 落盘(文件头标注
    "提取自 <原文件路径>",原路径留档备查)。**禁止假装读懂了二进制、禁止凭文件名猜内容**——
    需求文档是需求质询与提案规格步的输入,读不了的文件喂进去,后面全流程都在编;
  ② 用户只有一段描述(对话中粘贴/口述) → **禁止用 Bash/PowerShell/echo/重定向自行写文件**
    (Windows 默认编码曾把中文写成乱码并导致确认死循环)。先执行 `mae-flow messages`，找到承载需求原文的
    消息 ID，再执行 `mae-flow requirement-record --message-id <ID> --ticket <单号>`。工具会原文照录为
    UTF-8、写入正文指纹并回读校验；把生成文件路径与内容摘录放进最终配置确认单;
    如果已有的是 GBK/UTF-16 文本，执行
    `mae-flow requirement-record --source "<原文件>" --ticket <单号>` 规范化；二进制仍按 ① 处理。
  ③ 用户没有任何需求材料 → 停:需求是交付的前提,请用户提供路径或口述;**禁止替用户发明需求**。
  候选列举纪律:**默认不扫描仓库凑候选清单**(选择空间本身就是引导);仅当用户明说"帮我找找"
  才定向搜索,列出的每个候选必须标注来源并附摘录供核对。
  done 时状态机硬校验:需求文档必须真实存在、可严格按 UTF-8 读取、无高置信乱码；由
  requirement-record 生成的文件还会核对正文 SHA-256。配置和确认全部通过后才一次性保存，
  失败不会留下半套配置。乱码不是用户确认问题，禁止反复让用户说“我确认”
- 编译方式(Mae-Flow 自带 build-fix skill | mvn compile -q | 其他)——按仓库构建体系推断候选,
  用户拍板；C++/CMake/mcde 仓推荐 build-fix，Java/Maven 仓推荐明确的 mvn 命令。
  build-fix 随 Mae-Flow 插件提供，不单独安装、不做项目目录迁移、不要求 reload；
  Java/Maven 仓 → mvn 命令;其他 → 用户给命令。拿不准就和用户确认一条能跑通的编译命令兜底。
  **该配置是全流程唯一编译路由**:compile-agent、codecheck/UT agent 的编译验证全按它执行,
  任何 agent 现场另猜编译命令都是违规;
- UT生成方式:自动推断后放进最终配置确认单(C++/mcde→插件自带 AutoUT skill;Java/Maven→插件自带
  java-autout skill;其他→参考仓内写法)。这些能力随 Mae-Flow 安装，不再单独安装或 reload
- UT运行命令提示(随生成方式确定 | mvn test | 其他)。这是运行入口提示，不是逐字字符串门禁；
  最终以真实执行结果为准
仓库预设:current 输出若附带「仓库预设(.mae-flow-defaults.json)」块(团队提交进仓的恒定项,
如编译方式/UT生成方式/UT运行命令),以其值为预填直接进入确认展示,不再重新推断;
预设只用于填候选值，最终仍以完整配置确认单为准。缺少事实时可以提问取得值，但**不要逐项让用户说确认**；
任何一个单项回答也不能给整份配置背书。
值全部明确后，执行 current 最后给出的 `config-review --set ...`。脚本会统一校验八项配置、派生分支名、
展示需求内容摘录并生成绑定配置指纹的确认单；失败不会写入已确认配置。

然后严格按 config-review 输出，用**一次** AskUserQuestion 完成当前四项开场决策（一卡合一：把开场的
四次停顿并成一次，后续三步直接消费本卡答案）：

- Q1「上述完整配置是否正确？」选项固定：“确认以上全部配置 / 需要修改”；
- Q2「交付方式？」选项：完整开发 / 已定位问题修复 / 局部修改 / 处理评审意见
  （推荐项排第一并给一句依据；review 仅限已交付单）；
- Q3「是否做需求质询？」选项：做质询 / 跳过（仅完整开发生效；需求材料单薄时推荐做质询——
  材料越薄缺口越多，跳过等于让 AI 替用户脑补需求）；
- Q4「STORY 如何交付？」选项：生成并入库 / 生成但不入库（本地交测） / 不生成
  （仅完整开发生效；团队通常只需本地交测时推荐第二项）。
用户答完后：Q1 为确认则执行输出的简短 `done`（按钮结果由 harness 自动读取）；Q2-Q4 的答案在
随后的 workflow_select / grill_ask / story_ask 步骤**直接 done --choice 消费，不再重复提问**
（验真读取的是本卡捕获的真实用户选择）。不要再次要求用户输入确认句。用户选择修改则修正对应值
并重新 config-review，旧确认自动失效。Q2 选了非完整开发时，Q3/Q4 的答案自然不会被用到。

交付方式确定后，紧接着的 `code_reviewer_ask` 用一张单问题卡询问是否启用独立 CODE Reviewer。
AskUserQuestion 单卡最多四问，因此禁止把它硬塞回上述四问卡导致工具报错。

若 CodeAgent 没把 AskUserQuestion 选择结果回传给 Hook，让用户发送一条普通消息“确认以上全部配置”后原样
执行 done 即可。确认失败只会停止 Agent 重复执行同一条错误命令，流程不会锁死，不需要 exit、删除状态或重新
init；执行 `messages` 可直接看到脚本提取到的真实答案。用户确实不想继续时仍可发送 `/mae-flow:mae-flow exit`。
