# 编码基准 v1（审美目标）

定位：这是**目标状态**，不是门禁。lightcheck 与 CodeCheck 守下限（能编译、无告警、
不超机械限值）；本文件描述"好"。主 Agent 写每一块前后对照自查，Craft Reviewer 按本单
逐条检查。所有条目服从一条总纲：**代码是写给下一个读它的人的，那个人默认不是你**。

## 1. 顺应优先于自包含

动笔前先找仓内同类实现。已有的抽象能用就用、能扩展就扩展；只有说得出"既有的为什么
不够"时才新建，并把理由写进实施附录。

- 坏：仓里已有 `OrderUtil.parse()`，新代码又写了 `OrderHelper.doParse()`，两套并存
- 好：调用或扩展 `OrderUtil`；确需重写时先删旧的（删除是改动的一部分）

## 2. 命名从邻居继承，同一概念全程一个名字

新文件的命名风格抄同目录邻居，不自创方言；一个概念在本次改动里只允许一个名字。

- 坏：同一份配置在三处分别叫 `cfg`、`config`、`settings`；仓里都叫 `Repo` 它偏叫 `Dao`
- 好：先看邻居怎么叫，跟着叫

## 3. 错误处理：防御在边界，一次到位，错误带上下文

入口校验一次并给出带上下文的错误；内部代码信任已建立的不变量，不逐层重复判空。
吞掉异常等于把调试成本转嫁给未来的值班人。

- 坏：每层都 `if (x == null) return null;` —— 错误无声传播，最终在离根因十万八千里处爆掉
- 坏：`catch (Exception e) { log.warn("failed"); }` —— 丢上下文、吞栈、继续跑
- 好：边界处 `Objects.requireNonNull(order, "order from mq payload")`；内部直接用

## 4. 函数按概念拆，不按行数拆

lightcheck 的 50 行是下限不是刀。每个函数名必须是一个能独立陈述的职责；
如果拆出来的函数说不出自己"是什么"，那次拆分就是机械的。

- 坏：`doWork1/doWork2/doWork3` 各 49 行，互相传 7 个参数
- 好：`validateQuota() / reserveStock() / emitAuditEvent()`，各自能单独解释

## 5. 不写投机的灵活性

没有第二个调用方之前：不抽接口、不加配置开关、不留"以后可能用"的参数。
可扩展性来自清晰的职责边界，不来自预埋的钩子。

- 坏：单实现的 `XxxStrategy` 接口 + 工厂 + 配置项，全仓只有一个分支
- 好：直接写那一个实现；真出现第二个变体时再抽——那时才知道变化轴在哪

## 6. 布尔参数是坏味道

`send(order, true, false)` 在调用点读不懂。两个以上布尔参数几乎必然是两个函数
被硬挤在一起。

- 坏：`export(data, true /*compress*/, false /*async*/)`
- 好：拆成 `exportCompressed(data)` / 用枚举 `export(data, Mode.COMPRESSED)`

## 7. 对称性：相似的事看起来相似

新增第 N 个 case/分支/处理器时，先读前 N-1 个，让新的长得像旧的——结构、顺序、
错误处理、日志格式全部对齐。读代码的人靠差异发现逻辑，无意义的差异是噪音。

- 坏：前三个 handler 都是"校验→转换→落库"，第四个顺序倒着来还多包了一层 try
- 好：第四个与前三个逐段可对照，真正的业务差异一眼可见

## 8. 删除是一等操作

改动使旧代码失效时，删掉它：不注释掉、不留 `_old` 后缀、不留"暂时保留"的死分支。
ponytail 会兜底，但兜底不是授权。

## 9. 注释解释为什么，不复述代码

按 `comment-standard-v1.md` 执行：新增业务注释用简体中文，写"为什么这样做/为什么
不那样做"；逐行翻译代码的注释一律不写。遗留问题用 `TODO(<问题单>)` 留痕。

## 10. 每块写完的四项自查（与 build 步骤一致）

1. 命名与邻居文件一致？
2. 有没有和本次已写、或仓内已有重复的 helper？
3. 错误路径处理与本模块惯例一致？
4. 暴露给后续块的接口，签名此刻定稿？
