# Mae-Flow

Mae-Flow 是一套给 CodeAgent 使用的代码交付流程。

当前版本：`2.1.0`。版本变化见 [CHANGELOG.md](CHANGELOG.md)。

你给出单号和需求，它会先把需求问清楚，再做设计、编码、编译、CodeCheck、单元测试和推送。中间需要你
决定的地方会停下来问，不该由 AI 自己决定的事，它不能悄悄替你做。

它解决的不是“让 AI 多写几份文档”，而是三个很实际的问题：

- 需求没说清楚就开始写，越到后面返工越多；
- 流程很长，AI 容易忘步骤、忘约束，甚至做完了才发现没编译；
- 会话中断、上下文变长或者换了模型以后，前面的进度和判断容易丢。

Mae-Flow 把流程进度、允许做的事和检查结果都记在项目里。AI 每次只处理眼前这一步，不靠它从头记到尾。

> 只安装插件不会接管项目。没有主动发起 Mae-Flow 时，改代码、执行命令和使用子 Agent 都照常进行。

## 它能做什么

| 你现在要做的事 | 入口 | 实际会发生什么 |
|---|---|---|
| 开发一个新需求或修复一个缺陷 | `/mae-flow` + 单号 + 需求 | 从需求澄清一直做到分支推送 |
| 处理已经交付过的评审、走读或流水线意见 | `/mae-flow review-fix` | 先逐条查证意见，再做增量修改、编译、检查和测试 |
| 晚上交给 AI 连续开发，早上看结果 | `/mae-flow moonlight` + 需求 | 不再中途提问，尽力做到推送；做不完的如实写进晨间报告 |
| 只补并运行单元测试 | `/mae-flow ut` + 目标功能或文件 | 不启动完整流程，只生成和执行 UT，默认不提交 |
| 只做 CodeCheck | `/mae-flow codecheck` + 范围 | 先检查，0 告警直接结束；有告警才修，默认不提交 |
| 只把一段需求问清楚 | `/mae-flow grill` + 需求 | 一次问一个问题，最后留下澄清结果，不设计、不写代码 |
| 一个需求涉及多个代码仓 | `/mae-flow chain` + 单号 | 查清各仓触点、接口和先后顺序，生成各仓都能直接使用的启动说明 |
| 只补一份 STORY | `/mae-flow story` + 单号 | 根据已有需求产物补 STORY，不启动代码开发 |
| 只检查和安装环境 | `/mae-flow setup` | 运行同一套可重复执行的安装与检查脚本，不开需求流程 |
| 不想继续走流程，直接改代码 | `/mae-flow exit` | 保存现场并立即退出，不回滚代码，不再受流程门禁限制 |
| 忘了怎么用 | `/mae-flow help` | 根据本说明给出入口和下一步 |

独立 UT、CodeCheck 和需求质询可以直接处理未提交代码，不要求单号和分支。它们不会创建完整交付状态，
也不会顺手替你提交或推送。

完整交付里还会自动处理这些容易漏掉的事情：

- 按团队规则创建分支、组织提交并推送；
- 根据需求说明生成给测试使用的 STORY，由你决定是否入库；
- 精简 AI 写出的重复和膨胀代码；
- 在状态栏持续显示单号、步骤和分支；
- 会话中断后从原步骤恢复，不用让新会话重新理解全量历史；
- 结束时整理本仓真正值得复用的构建、测试和排障经验。

## 30 秒开始

在项目仓库中打开 CodeAgent，发一句：

```text
/mae-flow
交付 REQ2026071801，需求文档在 docs/se/xxx.md
```

没有文档也没关系，一句话需求也可以：

```text
/mae-flow
交付 DTS2026071902。删除好友时没有清理会话缓存，偶尔会崩溃。
```

后面你只需要做三件事：

1. 回答它确实拿不准的需求问题；
2. 在需求说明、实现范围和遗留问题这些确认点上做决定；
3. 分支推送后去代码平台创建 MR，跟进流水线和合入。

流程运行中不用反复敲 `/mae-flow`。直接回答、说“继续”、问进度都可以。会话崩了、清空上下文或电脑重启
也没关系，新会话里说“继续之前的交付”，它会从磁盘上的断点接着走。

## 一次完整开发会经过什么

```text
确认项目和运行方式
        ↓
把需求问清楚
        ↓
确认需求说明
        ↓
设计实现方案
        ↓
分批编码和编译
        ↓
CodeCheck、UT、需求对照
        ↓
确认结果并推送
```

### 1. 确认项目和运行方式

先实测环境，再确认单号、基线分支、需求材料、源码范围，以及项目究竟怎么编译、怎么生成和运行 UT。
这些内容后面会统一复用，编译 Agent 和 UT Agent 不能到现场再猜另一套命令。

第一次使用时，能自动完成的安装会自动完成。确实需要人操作的步骤会把目录和命令说清楚，不会让 AI
自己乱初始化项目。

### 2. 把需求问清楚

AI 会先读需求和相关代码，然后一次问一个问题。它不会只问完预先准备的清单就结束：你的回答如果带出
新的名词、边界、异常场景或前后矛盾，它会顺着继续追问。

这一阶段要说清楚的是：做什么、不做什么、输入输出、异常情况、兼容要求和验收标准。

### 3. 确认需求说明

讨论结果会整理成正式的需求说明，并把三类内容分开：

- 已经由你确认的事实；
- AI 根据代码做出的推断；
- 仍然需要你决定的地方。

这里需要认真看一遍。后面的设计、编码和测试都以这份说明为准。需求说明错了，后面跑得再顺也只是把
错误实现得更完整。

### 4. 设计实现方案

AI 会查清要修改的模块、现有调用关系、数据如何流转、异常怎么处理，以及会不会影响已有行为。方案确认后，
再拆成可以逐步完成的开发任务。

小而明确的修改会减少前期工作；跨模块或行为变化较大的需求会做完整分析。AI 会说明建议和理由，由你确认，
不会自己偷偷选一条省事的路。

### 5. 分批编码和编译

编码按任务分批进行，每批解决一个相对独立的问题。每批完成后，使用第一阶段确认过的项目方式编译。

编译、长日志和反复修复交给专门的 Agent，主会话只接收结论和真正需要关注的问题。复杂 UT 也会分批生成：
先写一部分、编译运行通过，再继续下一批，避免一次生成太多以后大面积返工。

### 6. 检查和测试

代码完成后会依次做：

1. 清理重复实现、临时调试代码和不必要的膨胀；
2. 运行 CodeCheck，0 告警直接继续，有告警才启动修复；
3. 生成并真实运行 UT，不接受“测试文件写完了但没有跑”；
4. 把最终代码和需求说明逐条对照，检查漏做、做偏和擅自增加的行为。

如果 UT 暴露出被测代码可能有问题，AI 必须先自行调查，再把证据和倾向判断交给你。由你决定是修源码、
修测试，还是另开问题处理。CodeCheck 告警也不能由 AI 自行豁免。

只要源码或测试发生变化，绑定旧代码的编译、CodeCheck 和 UT 结果就会失效，需要重新验证。这样可以避免
“前面编译通过，后面又改了代码，最后仍拿旧结果交付”的情况。

### 7. 确认结果并推送

最后会展示改了什么、检查结果、遗留问题、提交列表和准备推送的分支。确认后再推送。

新需求还会在结束前确认需求说明是否定稿。夜间无人值守模式不会替你做这个不可逆决定，它会停在晨间检查，
等你看完结果后再继续。

## 不想跑完整流程时

### 只补 UT

```text
/mae-flow ut
给 src/probe/GeoInfoManager.cpp 当前改动补边界测试
```

启动前必须定位至少一个被测业务文件，不能拿空范围或只有测试文件的范围开工。脚本会列出完整文件清单，
你需要再确认一次。确认之前不会生成测试，也不会派 UT Agent。

确认后才会按项目已经配置好的生成方式和运行命令工作。任务通过代表测试真实执行并全绿，不只是生成了文件。

### 只做 CodeCheck

```text
/mae-flow codecheck
检查 GeoInfoManager 这次修改
```

没有点名文件时，默认从当前工作区改动中找业务代码；测试文件自动排除。实际清单同样会展示给你二次确认，
确认前不会运行 CodeCheck。

0 告警直接结束。有告警才派专门的修复 Agent；认为某条不该改时只能报告原因，不能自动写豁免。

### 只把需求问清楚

```text
/mae-flow grill
支持按名称查询基站，具体边界还没想清楚
```

这个入口只做需求澄清。主 Agent 负责和你对话，另一个只读 Agent 会在开始和结束时各检查一次有没有漏问。
最终只留下澄清结果，不进入设计和编码。

### 调整或取消独立任务

UT 和 CodeCheck 的范围确认页有两个选择：

- **确认以上范围**：冻结该清单并开始执行；
- **需要调整范围**：取消当前任务，按新范围重新发起。

Agent 不能在你确认后静默扩大文件范围。任何独立任务都可以用 `/mae-flow cancel` 取消；已经产生的代码和
报告会保留，普通开发不会被拦。

## 月光宝盒：晚上跑，早上看

白天限流严重，或者你不想守着每个确认点时，可以在新需求或进行到一半时切换：

```text
/mae-flow moonlight REQ2026071801，需求是……
```

进入后不再向用户提问。它会根据已有需求、代码和项目配置采用保守判断，继续分析、编码、编译、CodeCheck、
UT 和推送。

这里的目标是“尽力做到可以让人早上接手”，不是把失败包装成成功：

- 能修的问题先真实修；
- 有限尝试后仍解决不了，记录现象、尝试和风险，再继续后面的步骤；
- 不会自动豁免 CodeCheck，不会删掉、禁用或过滤失败测试；
- 会尝试推送，但认证、网络或冲突失败时只保留现场，不会谎报已推送；
- 推送后停在晨间检查，不自动定稿需求。

早上常用三个入口：

| 入口 | 作用 |
|---|---|
| `/mae-flow moonlight report` | 看完成内容、自动判断和遗留问题 |
| `/mae-flow moonlight repair` | 根据报告继续修，再重新走后续检查和推送 |
| `/mae-flow moonlight finalize` | 结果满意后进入最终确认 |

报告保存在 `.mae-flow-work/moonlight-report.md`，不进入业务提交。

## 评审意见和跨仓需求

### 已经有 MR，又收到评审意见

使用 `/mae-flow review-fix`，把意见原文贴进来。

AI 会先查代码和规格，再逐条给出结论：需要修、可以有依据地回复，或者这条意见其实改变了需求，应该转成
新的开发轮次。确认后只处理本轮增量，再编译、CodeCheck、补测和推送，提交会追加到原 MR。

### 一个需求涉及多个代码仓

先使用 `/mae-flow chain REQxxx`。

它会从关键词、调用链和配置入口几个方向查触点，再和你确认各仓职责、接口字段、错误语义和交付顺序，
最后生成一份链路说明和每个仓的启动卡。之后每个仓各自运行完整流程，使用同一份链路说明作为需求输入。

如果任一仓开发过程中发现链路说明有遗漏，应先修订说明并同步其他仓，不能让这个仓自己悄悄绕开约定。

## 中断、退出和重新启用

### 会话断了

说“继续之前的交付”。状态保存在项目里，不需要依赖旧对话。

### 不想再走流程

直接发送：

```text
/mae-flow exit
```

这条消息本身就是授权，不会再问你一次。退出会保留全部代码、提交和文档，并把流程现场放到
`.mae-flow-work/exited/`。退出后可以直接让 AI 改代码或补 UT，原流程不再强制编译、检查和提交。

如果 Hook 本身损坏，命令会给出一个需要你在真实终端输入 `EXIT` 的紧急出口。不要手删
`.mae-flow.json`：手删既没有留档，也不能保证所有控制状态一起退出。

### 想重新接回原流程

明确说“重新接回 Mae-Flow”。恢复时会检查退出期间代码有没有变化；变过就回到相应的编译和检查入口，
退出前的旧结果不会复用。普通的“帮我改一下代码”不会被解释成重新启用流程。

## 它是怎么保证 AI 不乱跑的

提示词只负责告诉 AI 应该怎么做，真正的约束由程序完成：

- 当前走到哪一步、下一步是什么，由状态文件记录；
- 不该改源码的阶段，编辑操作会在真正发生前被拦下；
- 分支名、提交信息、需求文档结构和检查结果都会实测，不接受 AI 口头说“完成了”；
- 编译、CodeCheck、UT 使用带文件范围和代码指纹的任务卡交给专项 Agent；
- 用户确认来自真实用户消息，Agent 不能自己填写“我确认”；
- 检查结果绑定当时的代码，代码一变，旧结果自动失效；
- 每一步都能从磁盘恢复，不依赖主会话长期记忆。

这些门禁是为了阻止未经确认的动作，不是为了把流程卡死。专项 Agent 的收尾因为宿主兼容问题无法识别时，
会展示真实风险，让你选择重试或承担风险继续；CodeCheck 输出格式变化时可以保存原始报告后人工确认；
任何阶段都保留 `/mae-flow exit`。

## 第一次使用和环境准备

Mae-Flow 面向 Windows 开发环境。开始前请自行准备：

| 基础软件 | 最低要求 |
|---|---|
| Python 3 | `python --version` 能正常输出 |
| Git for Windows | `git --version` 能正常输出，并包含 Git Bash |
| Node.js | 20.19 或更高 |

第一次开单会自动做环境检查。通常会经历：

1. 检查基础软件；
2. 配置公司 npm 与 Git 环境；
3. 安装流程需要的 CLI 和插件，已经安装的直接跳过；
4. 检查项目级配置；
5. 给出需要用户手工完成的初始化命令；
6. 最后重新实测一遍。

安装脚本是幂等的，可以反复执行。想提前准备，可以运行：

```text
python "<插件目录>/scripts/setup.py"
```

完整日志在 `%TEMP%\mae-flow-setup.log`。

脚本会逐项核对 npm、Git 和项目配置，不会因为“键存在”就把错误值当成正常。需要修改全局 npm/Git
网络配置时，会先把原值保存到 `%TEMP%\mae-flow-setup-config-before-*.json` 并显示路径。OpenSpec 和
Comet 使用本版实测过的固定版本；CodeCheck 来自公司内网仓库，实际安装版本会写入安装日志。

有两类操作必须由人完成：

- Python、Git、Node 等基础软件缺失时，由用户安装；
- 项目第一次初始化时，按提示在指定目录运行给出的命令并选择 CodeAgent 对应平台。

初始化命令不会由 AI 自动执行，避免一次生成大量无关平台目录。安装或目录迁移完成后，如果提示刷新技能或
重启会话，请照提示操作；回来只要说“继续”。

团队可以把稳定的项目配置写进 `.mae-flow-defaults.json` 并提交：

```json
{
  "编译方式": "项目真实编译命令或 build-fix skill",
  "UT生成方式": "AutoUT",
  "UT运行命令": "项目真实 UT 命令",
  "测试路径": ["测试目录正则"],
  "源码路径": ["源码目录正则"]
}
```

后续开发者只需要确认，不用每次重新猜。

## 常见问题

### 为什么 AI 停下来了？

大多数时候是在等你确认，不是卡住。看它最后展示的问题或选项，做出选择即可。

### 为什么提示“证据不足，拒绝推进”？

说明它声称完成的事没有对应到真实文件、命令结果或专项 Agent 报告。让它按报错补证据。相同问题重试代价
很高时，系统会给出用户承担风险继续的出口，不需要无限循环。

### 中文需求文件乱码，怎么确认都过不去？

不要继续说“我确认”，确认不能修复坏文件。让 AI 执行 `mae-flow doctor`。口述需求会通过确定性命令写成
UTF-8；已有 GBK/UTF-16 文本也可以规范化后再确认。连续两次失败会停止重复提问，并给出退出入口。

### AI 在不该改代码的阶段被拦了

这是正常的阶段保护。如果你就是不想走流程，发送 `/mae-flow exit`；如果只是想并行处理另一件事，建议用
`git worktree` 新开一个工作目录，避免把无关代码混进当前 MR。

### 一个目录能同时跑两单吗？

不能。一个工作目录只有一个有效流程。并行开发请使用不同的 `git worktree`。

### 专项 Agent 跑了很久，最后因为格式问题不让继续

先让 AI 展示拒绝原因。可以低成本重答就重答；宿主没有提供完整收尾记录或重跑成本很高时，让 AI 给出
“重试 / 承担风险继续”选项。风险确认只放行当前任务卡和当前代码，不会把其他检查一并关掉。

### 怎么看现在走到哪了？

状态栏会显示单号、当前步骤和分支。也可以直接对 AI 说：

| 你说的话 | 用途 |
|---|---|
| `执行 mae-flow current` | 看当前步骤该做什么 |
| `执行 mae-flow status` | 看原始状态 |
| `执行 mae-flow doctor` | 做完整体检，排障首选 |
| `执行 mae-flow report` | 看本单各阶段耗时和流程摩擦 |
| `执行 mae-flow report --all` | 看本仓历史交付统计 |
| `执行 mae-flow envcheck` | 重新实测环境 |

Hook 日志位于 `%TEMP%\mae-flow-hook.log`。遇到无法解释的拦截，把 `doctor` 输出和日志最后几十行一起交给
维护者。

## 哪些内容会留下

根据任务类型，项目中可能产生：

- 需求说明和规格变更；
- 设计文档和实现计划；
- 业务代码与单元测试；
- 可选的 STORY；
