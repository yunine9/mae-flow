# Mae-Flow 轻量高质量工作流重构设计

- 状态：已批准
- 日期：2026-08-01
- 目标平台：Windows 插件为主，同时保持跨平台开发与测试能力

## 1. 背景

Mae-Flow 最初以 Comet 等项目的提示词和阶段方法为基础。为解决长流程遵从性不足、模型虚报和流程恢复问题，系统逐步加入状态机、证据令牌、任务卡、固定报告、Hook 校验和结果新鲜度检查。这些机制提升了可控性，但也形成了新的主要问题：

- 小型需求选择 Full 后可能运行一整天；
- Build、UT、CodeCheck 被重复调用，单次返工可能耗时一至数小时；
- Hook 依赖固定字符串、固定结构和未知工具输出，容易把正确工作打回；
- 状态机关注“证明执行过”，多于关注需求、设计和代码是否正确；
- 上游插件的长提示词和 Mae-Flow 自有规则相互重叠甚至冲突；
- 用户需要阅读大量过程文档并输入固定 ACK，投入与决策价值不匹配；
- 编译等待曾通过反复 sleep/poll 实现，不适合耗时且由内部工具同步封装的 Windows/C++ 构建。

本次重构保留历史质量能力与必要安全边界，移除不能直接提升交付质量的流程证明和重复劳动。

## 2. 目标与非目标

### 2.1 目标

1. 让开发同事以最少等待和最少人工介入完成高质量交付。
2. 保留需求质询、详细设计确认、可测试性设计、代码检视和质量工具的真实价值。
3. Build、UT、CodeCheck 等内部能力对流程保持黑盒；Mae-Flow 不猜测跨语言、跨版本工具的输出格式。
4. 昂贵操作默认只执行一次，不因流程证明失败而循环重试。
5. Hook 只保护高风险、不可逆或容易污染他人工作的边界。
6. 状态只服务于恢复和协作，不作为模型服从性证明。
7. 面向 Windows 插件验证路径、命令发现、进程等待和文件操作语义。

### 2.2 非目标

- 不追求与 Comet、OpenSpec、Superpowers 或 Ponytail 的命令、目录和工作流兼容。
- 不把任意上游 Skill 原文直接视为 Mae-Flow 的运行时合同。
- 不通过代码行数、文件数、函数数判断需求应该走 Full 还是 Focused。
- 不建立第二套长期并行的生产状态机。
- 不要求内部 Build、UT、CodeCheck 工具改变返回格式来适配 Mae-Flow。

## 3. 核心原则

1. **验证结果，不验证表演。** 需要证明的是用户预期、设计、代码和交付结果，而不是某段固定话术或某份过程文件是否存在。
2. **昂贵能力只调用一次。** 相同源码和相同环境下，Build、UT、正式 CodeCheck 不自动重试。
3. **用户拥有风险决策权。** 是否重跑昂贵能力、是否接受已知风险、是否纳入条件文档，由用户基于清晰信息决定。
4. **流程与 Skill 解耦。** 流程决定何时需要某类能力；Skill 自己决定如何完成其专业工作。
5. **语义风险决定流程深度。** 影响行为、兼容性、数据、安全、并发、接口或跨模块关系的变化需要更完整设计，不使用机械规模阈值。
6. **预期行为保留，历史机制可替换。** 旧机制只有在其保护的行为被分类并有新承载方式后才能移除。
7. **测试友好性必须在编码前设计。** 不在 UT 阶段才发现业务逻辑被框架、数据库连接或执行过程锁死。

## 4. 总体架构

Mae-Flow 只保留两条交付路径和一组独立工具动作。

### 4.1 Full

Full 表示结果完整，不表示所有步骤都必须制造停顿。它由六个可恢复阶段组成：

`Startup → Spec → Story → Construction → Quality → Delivery`

### 4.2 Focused

Focused 融合原 Hotfix、Tweak 和 Review：

- Bug：先理解现象与根因，再做范围明确的修复；
- 小型行为变更：确认边界后直接修改；
- Review 修复：先查证意见，再决定修复、解释或转入设计；
- 一旦出现行为不清、跨模块设计、兼容性、安全、数据或接口风险，向用户说明并升级 Full。

升级由语义风险决定，不由代码规模决定。

### 4.3 独立工具动作

UT、CodeCheck、Grill、Story 和 Chain 可作为一次性工具使用：

- 不创建迷你状态机；
- 不签发任务卡、SHA 或证据令牌；
- 不要求固定报告格式；
- 不自动重试、提交或推送；
- 输出由主 Agent 和用户直接消费。

## 5. Full 详细流程

### 5.1 Startup

一次性展示并确认：

- 当前需求与工作目录；
- Full 或 Focused 建议及原因；
- Continuous 或 Staged 提交节奏；
- 已存在未提交文件及其归属；
- 预计需要的 Build、UT、CodeCheck 等昂贵能力。

用户可以自然语言修改任何决定，不需要固定 ACK。

### 5.2 Spec：确认 WHAT

主 Agent 读取需求、相关代码和当前行为基线。Grill 只处理需求层问题：输入、输出、前置条件、边界、失败行为、兼容性、并发、非目标和可观察验收标准。

Grill 保留以下原则：

- 事实从代码和环境中查，不把可查事实问给用户；
- 决策逐个询问，一次只问一个；
- 每个问题附证据、影响和推荐答案；
- 回答可能产生新的决策树分支；
- 不进入类、函数、文件或实现方案等 HOW 层内容。

Full 在 Spec 确认前固定运行一次轻量、只读的 Grill critic。critic 检查遗漏、矛盾、不可测试表述和 WHAT/HOW 混杂：

- 有真实缺口时，主 Agent 整理后继续逐项询问用户；
- CLEAR 时不增加用户停顿；
- critic 失败时记录事实，不重试、不阻断；
- 不需要备课文件、任务卡、SHA、固定字段或 Hook 证明。

最终 Spec 使用可观察、可测试的行为描述。用户在一个清晰的 Spec 确认点完成检视。

### 5.3 Story：确认 HOW

Story Design 基于已确认 Spec 和实际代码生成，继续使用现有 Story 模板表达：

- 实现边界与主要代码落点；
- 关键流程、类职责与依赖关系；
- 兼容性、错误处理、生命周期、所有权和并发考虑；
- 可测试性设计与需要提前创建的 seam；
- CP 划分建议及风险。

Story 必须考虑“稳定框架与变化业务分离”。例如数据库逻辑应尽量把连接获取和执行框架留在薄编排层，把查询条件、SQL 构造和结果映射提取为可直接测试的业务单元；不为了覆盖率强行 Mock 十几年历史框架。

Story 经过一次轻量 Design Reviewer 检视。主 Agent 查证并整合意见后，把最终方案和重要取舍呈现给用户。用户可以自然语言修改。Story 默认只保存在本地工作包，不提交，除非用户明确要求。

### 5.4 Construction：按 CP 编码

Story 确认后生成简洁 CP 施工图。每个 CP 描述：

- 要完成的行为与边界；
- 精确到文件的预计修改位置；
- 关键设计动作；
- 为最终 UT 提前创造的可测试性条件；
- 完成判断和可能影响。

CP 不写逐行编码剧本，不把一行代码扩写成几十行文档。用户一次确认 CP 图和 Continuous/Staged 节奏。

编码遵循工程品味原则：优先兼容和清晰语义，明确所有权、错误、生命周期和并发；在实际约束下使用最简单设计；既有风格是证据但不是绝对权威；避免投机抽象，同时主动拆出真正有测试价值的确定性业务逻辑。

每个 CP：

1. 主 Agent 实现；
2. 执行低成本 Lightcheck 并顺手修复安全问题；
3. 最多进行一次 CODE reviewer 检视；
4. 记录与最终 UT 有关的实际设计和覆盖建议；
5. Staged 模式下，经用户确认后按精确文件清单本地提交。

CP 不写、不编译、不运行 UT。UT 交接信息累积到 `.mae-flow-work/<ticket>/ut-handoff.md`，不设固定格式和哈希门禁。

### 5.5 Quality：一次性质量链

正常顺序为：正式 CodeCheck → Build → UT。

跨 CP 集成审查仅在存在跨模块耦合、共享状态、接口变化或后期设计变化时运行，不作为固定仪式。

#### Lightcheck

Lightcheck 是 Mae-Flow 自有的廉价预检。Lizard 继续提供函数发现和结构解析。检查范围聚焦本次触及的代码，并保持 fail-open：解析失败应提示，不阻断开发。

必须保留与内部正式 CodeCheck 对齐的项目：

- 参数数大于 5；
- 有效函数行数大于 50；
- 控制嵌套深度大于 5；
- 变更行长度大于 120；
- 魔鬼数字缺少命名或明确意图说明。

魔鬼数字不设置“常见值可忽略”白名单；通过命名常量或就近注释说明语义即可。若触及的存量函数本来就违反正式 CodeCheck 阈值，也应展示。安全的小问题由主 Agent 顺手修复；需要大规模、高风险重构的项目进入正式 CodeCheck 处置清单，不为 Lightcheck 单独创建子流程、重新编译或复验。

#### 正式 CodeCheck

- 保留 fullcheck 精确定位本次变更文件和函数的能力；
- 只执行一次；
- 主 Agent 对每项结果给出明确去向：已修复、误报、存量问题、范围外、当前不安全；
- 不自动派发 fixer，不自动复验；
- 工具输出未知、异常或失败时如实展示，不通过 Hook 猜测格式并打回。

#### Build

- 调用 build-fix Skill 并等待其同步返回；
- 不 sleep、不轮询；
- Flow 不解析 Maven/g++ 封装的私有输出；
- build-fix 负责其 Skill 合同内的编译修复；
- 同一源码和环境失败后不自动循环重试。

#### UT

- UT Skill 接收 Spec、Story、累计 UT handoff 和最终 diff；
- UT Skill 自己负责写 UT、编译 UT 和运行 UT；
- Flow 不假设 gtest 或其他语言测试框架的具体输出；
- 存量 disabled/skipped、弱 Mock 能力和内部框架限制由 UT Skill 与主 Agent 结合上下文解释，不以通用正则硬拦；
- UT 揭示源码问题时回到 Construction 修复，由用户决定需要重跑哪些昂贵能力，不自动回放整条质量链。

#### 结果新鲜度

源码变化不会机械使全部结果作废：

- 文档或注释修改通常可复用已有结果；
- 仅测试代码变化不自动作废 Build；
- 影响相关生产代码、构建配置或测试语义时，主 Agent 说明影响并建议受影响能力；
- 判断不清或重跑昂贵时，由用户决定。

### 5.6 Delivery

最终一次性展示：

- 实现了哪些行为；
- Spec/Story 与实际实现是否有偏差；
- Build、UT、CodeCheck 的真实执行事实和未决风险；
- 将提交、推送的精确文件清单；
- 默认不上库的本地工作文档。

用户自然语言确认或调整后执行提交和推送。

## 6. Focused 流程

Focused 的默认目标是快速完成修改并提交，不复制 Full 的所有阶段。

1. 展示问题理解、修改范围、风险判断和建议能力组合；
2. 用户一次确认或自然语言调整；
3. 主 Agent 调查、修改并运行 Lightcheck；
4. Build、UT、正式 CodeCheck、CODE reviewer 按语义风险选择，并在执行昂贵能力前让用户看到选择；
5. 最终展示结果、风险和精确提交清单。

Focused 的最低质量底座是 Lightcheck、主 Agent 自审和精确 Git 归属。它不能因为“轻量”而绕过危险操作与提交安全。

## 7. 用户介入点

Full 的正常用户介入点只有：

1. Startup 配置；
2. Spec 确认；
3. Story 确认；
4. CP 图和提交节奏确认；
5. 最终交付确认。

条件介入仅用于：真实需求歧义、重要设计偏离、Reviewer 提出的真实取舍、昂贵能力重试、不可逆风险或提交清单变化。

所有确认支持自然语言，不要求精确 ACK、固定选项或用户复述系统文本。

## 8. 状态与 Hook

### 8.1 状态模型

状态是恢复游标，只记录：

- 当前路径、阶段和 CP；
- Spec、Story、UT handoff 等产物路径；
- 用户已做出的语义决策；
- 未解决风险；
- Build、UT、CodeCheck 等能力的调用与返回事实；
- 精确交付清单和提交节奏。

不再记录任务卡、报告哈希、证据令牌、固定 ACK、格式校验锁和“一字符变化全部过期”的链式状态。

### 8.2 Hook 职责

生产宿主合同是 CodeAgent 插件提供的同步 `Task`、`Agent`、`Skill`，以及
`SessionStart`、`UserPromptSubmit`、`PreToolUse`、`PostToolUse` Hook。Mae-Flow
不为 Codex 的异步 `spawn_agent` 建立完成事实，也不要求把内部 `build-fix`
Skill 复制进本仓；宿主对已配置 Skill 的同步返回就是不透明调用事实。

只保留四类 Hook 职责：

| 事件 | 职责 |
| --- | --- |
| SessionStart | 展示恢复摘要；由用户明确选择是否继续 |
| UserPromptSubmit | 捕获自然语言决定与退出意图；保存失败不阻止退出 |
| PreToolUse | 保护危险删除/Git、控制文件、编码授权边界和精确提交清单 |
| PostToolUse | 记录已预留 Git 副作用的实际结果；不解析 Agent/Skill 返回 |

黑盒能力由主 Agent 在真实同步调用结束后，通过一次
`advance capability-<outcome> --key <kind> --decision "<简短不透明摘要>"`
写入最小恢复事实。该动作不证明专业工具质量、不要求固定输出，也不会触发自动
复验；若状态记录失败，不得仅为补写事实重新执行昂贵能力。
调用前，主 Agent 必须读取当前能力尝试；同 kind 已有尝试且没有当前用户重试
决定时不再调用。该约束属于 Agent 行为合同，刻意不恢复 Agent/Skill Hook 门禁。

用户拥有的阶段确认和昂贵能力重试决定必须消费一条尚未使用的
`UserPromptSubmit` 事件。事件只证明本轮确实有用户自然语言输入；主 Agent
仍负责结合展示内容理解语义，不要求固定 ACK、关键词或复述系统文本。

`SubagentStop` 和 `Stop` 保持 CodeAgent 兼容注册，但只短路放行，不再承载流程合同。Hook 不解析 Agent 固定报告，不验证工具输出中的特定句子，不因为缺失过程文件阻止正常工作。

### 8.3 安全内核

PreToolUse 继续保护以下预期行为：

- 拦截危险删除、破坏性 Git 和宽范围 add/commit；
- Full 在进入 Construction 前、Focused 在用户确认初始修改范围前，不允许修改业务源码；确认后正常编辑，不做逐次源码写入审批；
- commit/push 只能包含用户确认的精确文件清单；
- 流程启动前已有脏文件不得被偷偷纳入；用户明确接管后才可纳入；
- Mae-Flow 控制文件不得被业务 Agent 随意修改；
- 状态损坏时普通工作可以继续，但 commit/push 必须重新获得精确清单确认；
- exit 永远可执行，并先释放工作流接管状态。

安全内核用于防止 CodeAgent 的常见误操作，不是对任意解释器、脚本语言或
恶意命令构造建立通用 shell 沙箱。已知写入器和控制文件目标应被识别；未知且
无法证明会写入的普通内部命令保持 fail-open，避免误拦私有 Build 包装器。

## 9. 文档模型

过程材料按需求分组，不平铺：

```text
.mae-flow-work/<ticket>/
  story.md
  ut-handoff.md
  review-notes.md
  delivery-notes.md

docs/mae-flow/
  requirements/<ticket>/spec.md
  requirements/<ticket>/story.md
  requirements/<ticket>/decisions.md
  requirements/<ticket>/engineering.md
  requirements/<ticket>/chain.md
  behavior/<domain>.md
```

- 核心 Spec 与当前行为基线是可持续使用的真相来源，正常纳入交付；
- Story 默认不上库；
- Story、决策、工程经验、CHAIN、评审账本、CodeCheck 豁免和交付笔记等条件文档，只有用户明确说 commit 才入库；
- 不再暴露 OpenSpec 名称、命令、固定标题和 archive 仪式；
- 每次交付直接更新当前行为基线，演进历史由 Git 保存。

## 10. Git 与 Moonlight

### 10.1 Git

- Continuous：最终一次 commit、一次 push；
- Staged：每个用户确认的 CP 使用本地 commit，最终一次 push；
- 每次提交逐文件列出；
- 禁止目录、通配符、`.`、`-A`、`--all` 和 `commit -a`；
- staged 集合必须与确认清单完全一致；
- 交付收据绑定确认时的源码基线、每个批准提交的前后 SHA 链和最终目标引用；
- 存量脏文件默认排除；
- 业务提交格式保持 `[单号][feat|fix]描述`。

### 10.2 Moonlight

Moonlight 是交互授权策略，不是独立状态机：

- 复用 Full/Focused 引擎；
- 昂贵能力同样只自动尝试一次；
- 活跃任务可以预授权精确业务文件的提交和推送；
- 条件文档只有被明确点名才包含；
- 存在未归属脏文件时可以继续工作，但不能自动推送。

## 11. 历史能力保全

首版不物理删除 vendored 插件。先建立并维护能力保全表：

| 来源 | 保留的质量能力 | 新承载位置 | 移除的流程负担 |
| --- | --- | --- | --- |
| Comet | 阶段目标、正确性审查、交付闭环 | 六阶段语义与 Reviewer 指引 | 上游运行时状态、guard、handoff、archive 控制 |
| OpenSpec | 当前/变更行为、可测试场景、WHAT/HOW 分离 | 原生 Spec 与 behavior 文档 | CLI、schema、artifact graph、固定格式、archive |
| Superpowers | 根因分析、评审意见先查证、完成前验证思想 | 精简的 Agent 指引和能力选择 | 强制 TDD、固定重试、SHA/计划/子 Agent 仪式 |
| Ponytail | 简洁、复用、标准库优先、避免投机抽象 | Construction 工程品味原则 | 最少文件/最少行数等机械目标与独立门禁 |
| grill-me | 逐支质询、事实自查、一次一问、带推荐 | Spec 阶段和轻量 Grill critic | 8 维落盘表、任务卡、固定报告、零问题强停顿 |
| Lizard | 函数发现和结构解析 | Lightcheck 运行时 | 无；它是解析器而非流程 Skill |

历史机制删除前必须满足：

1. 其保护的预期行为已经分类为“保留、薄替代、有意去摩擦或仅迁移使用”；
2. 保留能力已有新承载位置；
3. 对应语义回归通过；
4. vendored 源码、版本和许可证仍可用于核对和回退。

## 12. 迁移与故障处理

旧状态迁移到六阶段游标：

- 保留配置、Spec、Story、CP、用户决定和能力执行事实；
- 丢弃任务卡、哈希、证据令牌、固定报告和失败锁；
- 旧昂贵结果作为历史事实，是否复用按影响判断；
- 映射不清时展示恢复摘要并让用户决定，不自动推送；
- 旧状态在迁移前备份。

能力失败的统一处理：

1. 记录调用结果和简短不透明摘要；
2. 不自动重试；
3. 不因为无法解析输出而伪造 PASS 或 FAIL；
4. 主 Agent 说明已知影响与选择；
5. 只有用户再次授权后才执行第二次；源码或环境变化只作为影响说明。

对当前 CodeAgent 合同，Flow 不尝试计算内部编译器、测试环境或私有工具配置的
环境指纹。源码或环境变化只由主 Agent 向用户说明影响，不能自动产生重试资格；
任何已经尝试过的昂贵能力再次执行都必须消费新的用户自然语言决定。Grill 或
Reviewer 未启动、超时或未返回时只记录“已尝试”事实，不自动重试，也不阻断
用户继续确认 Spec 或 Story。

## 13. 验证与切换策略

新引擎先以测试专用路径运行，不长期维护双生产流程。语义回归至少覆盖：

- 实际只需少量代码的小型 Full 需求，不发生整日流程膨胀；
- 复杂需求经过 Grill、Spec、Story 和 CP 后保持行为与设计一致；
- C++/gtest 能力较弱、存在历史 disabled/skipped 的 UT；
- 正式 CodeCheck 输出未知、告警很多、误报或工具失败；
- 内部 Maven/g++ 构建同步成功、失败和超时；
- 同一源码不重复 Build/UT/CodeCheck，不出现 sleep/poll；
- 文档、测试和生产代码变化下的影响式结果复用；
- 存量脏工作区、精确文件提交和禁止宽范围 Git；
- 中断恢复、状态损坏、退出和再次进入；
- Windows 路径、命令发现、进程等待、编码和换行行为；
- Moonlight 精确授权与条件文档默认不上库；
- 历史插件能力保全表中的每项质量能力。

切换条件：

1. Windows CI 与核心跨平台测试通过；
2. 能力保全表完整；
3. 语义回归通过；
4. 旧安全行为均已分类；
5. 新状态迁移与退出路径经过故障测试。

满足条件后一次切换生产入口。旧实现与状态备份保留一个迁移周期，再依据真实使用反馈决定物理删除范围。

## 14. 成功标准

- 小型 Focused 修改不会被 Spec、Story、Build、UT 或正式 CodeCheck 的固定仪式拖慢；
- 小型需求即使由用户选择 Full，也只承担需求与设计确认的有效成本，不触发重复质量工具和证据返工；
- Full 仍能通过 Spec 和 Story 确认显著降低“需求到代码偏离”；
- 同一源码和环境下，每项昂贵能力最多自动执行一次；
- Hook 不再因固定话术、报告格式或未知工具输出导致返工；
- 任何退出请求都能立即退出；
- 用户只在高价值决策点介入；
- 每个提交都能精确说明文件归属，不夹带存量改动；
- 历史插件的有效质量能力有明确的新承载方式和回归证明；
- Windows 插件成为发布验收的第一目标环境。
